GpxilStudio

A gpxil file holds a genome as pictures: one pixel for every base of DNA, with a page for each chromosome and each kind of information – the reference’s bases, a person’s genotype, and how sure the calls are. GpxilStudio is a workbench for these files that runs entirely in your browser. You can look at a gpxil file, check it, make one from a person’s variants, draw any part of it, print it, get FASTA and VCF back out, and make pictures of a person’s own version of a gene and its protein. You can do all of this by pointing and clicking in the Tools tab, by typing commands in the Terminal tab, or by writing Python in the Notebook tab.

The formats, and the tools between them

A gpxil file is in the middle. A reference genome (FASTA) and a person’s variants (VCF) go in. Pictures, books to print, pictures of genes and proteins (pxil files), and FASTA and VCF again, come out. Each arrow is a tool: click one to open it, or click a box to see what you can do with that kind of file.

What there is to try

  • HG002’s chromosome 17 (/data/examples/HG002_chr17.gpxil.tif): the genome of a real person, from the Genome in a Bottle project’s benchmark, with their genotype at all 83 million bases. Its TP53 gene is a good place to start.
  • The GRCh38 reference (/data/grch38): a gpxil file for every human chromosome, read from the Gpxil browser’s web site a piece at a time, so nothing has to be downloaded first.
  • The worked example of the gpxil specification: ten bases, four variants, small enough to read pixel by pixel (The codes).
Your files stay on this computer

Python and the tools run inside this web page. Your files are kept in this browser, on this computer, and are never sent anywhere. The only things the studio reads from the web are Python itself, when it first starts, and the GRCh38 reference and the gene files, which come from the Gpxil browser’s site. Privacy has the details, and Your files explains how to keep copies.

A first session

Take ten minutes to see what gpxil files are and what you can do with them. You’ll look at the genome of a real person, HG002, around the gene TP53; draw it as a picture; see how this person’s TP53 protein differs from the reference’s; and make a small gpxil file of your own. Each step has a button that does it for you.

1 · Look at a genome

The Viewer tab shows a gpxil file as pixels, one for every base. This button opens HG002’s chromosome 17 at TP53, a gene that is mutated in many cancers. HG002 is a man whose genome has been sequenced in great depth by the Genome in a Bottle project, so his genotype is known very reliably.

Each square is one base, in rows that read from left to right and from top to bottom, like a page of text. In this view, Variants, the reference’s bases are faded, and the bases where HG002 differs from the reference stand out: orange where one of his two copies differs (heterozygous), red where both do (homozygous). Grey bases weren’t called with confidence. Point at a square to see what the file holds there.

One of the red squares is at chr17:7,676,154. There, the reference has G, and both of HG002’s copies have C. This is a common variant, rs1042522, which changes amino acid 72 of the TP53 protein from proline to arginine (P72R). Try the other views in Show, such as Haplotypes, which draws his two copies of the chromosome in two rows.

2 · See what is in the file

A gpxil file is an ordinary TIFF picture with many pages: one page for each chromosome and each plane. The ref plane holds the reference’s bases, gt the person’s genotype, flags extra facts such as which calls are phased, and gq, dp and ps how good each call is. What’s in a gpxil file, in the Tools tab, lists them. Press Run. The first run starts Python in your browser, which takes a few seconds; the very first time, it also downloads about 15 MB.

Under the form, The same in the terminal, and in Python shows exactly what the tool runs. You can use it to do the same job again without the form.

3 · Draw it as a picture

Draw a region as a picture writes the same kind of picture as a PNG file, which you can download or put in a document. The button fills in TP53 and the variants view.

4 · This person’s TP53 protein

Because a gpxil file holds the person’s genotype at every base, their own version of a gene can be read from it, spliced and translated into protein. Genes, transcripts and proteins as pxil pictures does this for each of HG002’s two copies of chromosome 17. Each picture has one pixel for each amino acid, and says how the protein differs from the reference’s. For HG002, both say differs from the reference: P72R.

The genes come from the Gpxil browser’s gene files (Ensembl, GRCh38), which are read from the web as they’re needed.

5 · A gpxil file of your own

Make a gpxil file (encode) turns a reference genome (FASTA) and a person’s variants (VCF) into a gpxil file. The specification’s worked example is tiny, ten bases and four variants, so you can see every pixel of the result.

It writes ~/genomes/worked-example.gpxil.tif. Press View under the result to look at it, then try Check, which checks it against the gpxil specification.

6 · The same in the terminal

Every step above is a command, so the whole session can be run again in one go. Run in the terminal types these commands into the Terminal tab and runs them.

gpxil info /data/examples/HG002_chr17.gpxil.tif
gpxil render /data/examples/HG002_chr17.gpxil.tif chr17:7661779-7687546 -o ~/results/TP53_variants.png --mode variants --width 256 --scale 2
gpxil2pxil /data/examples/HG002_chr17.gpxil.tif TP53 --kinds protein -o ~/results/pxil/TP53
gpxil encode /data/examples/worked-example.fa -v /data/examples/worked-example.vcf -o ~/genomes/worked-example.gpxil.tif
gpxil validate ~/genomes/worked-example.gpxil.tif

7 · Keep your work

Everything you make is kept in this browser, on this computer. To take it elsewhere, use a file’s Download button, or My files → Download all my files (.zip) at the top right. Your files has the details. Where next? The walkthroughs go through each job in turn, and Work with a gpxil file pixel by pixel, in Python shows how to get at the data yourself.

Big files and Python

gpxil files are big: a chromosome is tens of megabytes, a whole genome nearly a gigabyte. The studio never copies a file of 8 MB or more into Python’s memory. Python reads it where the browser keeps it, or from the web, a piece at a time, as it needs it. A big file that a tool writes goes the other way: it is handed to the browser to keep, and Python’s copy is freed. Big files and memory explains how this works and how to make the most of it.

Look inside a gpxil file, and check it

Someone has sent you a gpxil file, or you’ve made one. This walkthrough shows what it holds – its reference, its sample, its contigs and planes, its metadata – and how to check that it follows the gpxil specification. It uses HG002’s chromosome 17; with a file of your own, choose it instead.

1 · A first look, in the Files tab

Click a gpxil file in the Files tab. Without starting Python, the tab reads the file’s first page, where its metadata is, and shows what it holds: the reference it was made from, the sample, the layout, and a table of its contigs and their planes.

2 · Its pixels, in the Viewer

The Viewer shows the planes themselves. Choose a region and what to show; point at a pixel to see the values of every plane there.

3 · What’s in it, as gpxil says it

What’s in a gpxil file runs gpxil info. It gives the file’s format version, what wrote it and when, its reference and sample, and for each contig its length, its planes, how many VCF records went into it and how many entries its sidecar has (the inserted bases and complex variants that don’t fit in a pixel).

Tick All of its metadata, as JSON to see everything the file says about itself: each contig’s checksums (md5 and refget), the pages that hold its planes, how many bases were called with confidence, and the counts the encoder kept as it read the VCF, such as conflicts and ref_mismatches (both 0 here, as they should be). The gpxil format describes every key.

4 · Count what it holds

Count what a file holds runs gpxil stats: how much of each contig, or of a region, was called with confidence, and the person’s substitutions (with their ratio of transitions to transversions, Ti/Tv), insertions and deletions, how much is phased, and the quality and depth of the calls. HG002’s chromosome 17 is 86.9 % called, with 54,935 heterozygous and 34,713 homozygous substitutions and a Ti/Tv of 2.36. The Viewer counts the same for the region in view, under its key.

5 · Check it

Check a gpxil file runs gpxil validate. It checks the metadata against the specification’s JSON schema; that every contig has the pages its metadata names, of the right size and type; that every value of every plane is a code the specification allows; that the flags, phase sets and sidecar agree with each other; and, if you leave Recompute the sequences’ checksums ticked, that the reference plane’s bases give the MD5 and refget checksums in the metadata. That last check proves the bases are those of the reference the file names.

It should say Valid. An error means a reader can’t trust the file; a warning is worth reading but doesn’t make the file invalid. A file that isn’t gpxil at all, such as an ordinary TIFF picture, fails at once: its first page has no gpxil metadata.

6 · A file on the web

The files of the GRCh38 reference in /data/grch38 are on the Gpxil browser’s web site. Looking inside one reads only its first page, so it is as quick as a file of your own. Checking its checksums reads every base, which for chromosome 1 means downloading 67 MB, so untick Recompute the sequences’ checksums for a quick check of a big file on the web.

The same in the terminal

gpxil info /data/examples/HG002_chr17.gpxil.tif
gpxil info --json /data/examples/HG002_chr17.gpxil.tif > ~/results/HG002_chr17.metadata.json
gpxil stats /data/examples/HG002_chr17.gpxil.tif
gpxil validate /data/examples/HG002_chr17.gpxil.tif
gpxil info /data/grch38/chr1.gpxil.tif
gpxil validate /data/grch38/chrM.gpxil.tif

gpxil info --json prints the metadata as JSON; here it is saved in a file, which the Files tab shows neatly. gpxil validate --no-digests skips the checksums.

The same in Python

In a notebook, the metadata is a Python dictionary, and each contig an object with its name, length and planes:

from gpxiltools import GpxilFile
from gpxiltools.validate import validate

g = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")
print(g.metadata["reference"])
print(g.metadata["sample"])
for c in g:
    print(c.name, f"{c.length:,} bases", c.planes, c.entry["md5"])

report = validate("/data/examples/HG002_chr17.gpxil.tif")
print("valid" if report.ok else "not valid", report.errors, report.warnings)

Turn someone’s VCF into a gpxil file

A VCF file lists where a person differs from the reference. A gpxil file holds the whole of each chromosome, base by base, with the person’s genotype at every base. This walkthrough makes one from HG002’s variants around TP53, with chromosome 17 of GRCh38 as the reference, read from the web. Then it makes the same file without the reference’s bases, which is a hundred times smaller, and finally the specification’s worked example from a FASTA file.

What you need

  • The person’s variants: a VCF file (.vcf or .vcf.gz) with their genotypes. A VCF of several people is fine: you choose which one to encode.
  • The reference the variants were called against: a FASTA file, or a gpxil file with its reference plane, such as the chromosomes of GRCh38 in /data/grch38. Contig names are matched with or without chr, so 17 in a VCF finds chr17.
  • If you have one, a BED file of the regions called with confidence. Benchmark VCFs such as Genome in a Bottle’s come with one, and so do many variant callers’ outputs (as a gVCF, or a coverage BED).

1 · The variants

HG002_TP53.vcf holds the 206 records of the Genome in a Bottle benchmark (version 4.2.1) for HG002 between chr17:7,600,001 and chr17:7,750,000, around TP53. Open it to see what a VCF looks like: one line for each place where HG002 differs from the reference, with his genotype, such as 0/1 (one copy) or 1/1 (both).

2 · Why the regions called with confidence matter

A VCF lists the bases where a person differs from the reference, but says nothing about the rest. Some of the rest is like the reference; some wasn’t sequenced well enough to tell. Without more information, the encoder can only assume the person has the reference everywhere else – across the whole of chromosome 17, in this case, which this VCF can’t possibly tell us.

HG002_TP53.bed lists the 52 stretches, 140,254 bases in all, where the benchmark is confident of HG002’s genotype. With it, bases outside those stretches become UNKNOWN (no call) rather than the reference, so the gpxil file says exactly what is known and no more.

3 · Encode it

Make a gpxil file (encode) with the VCF, the BED file and chromosome 17 of GRCh38. The reference file holds only chromosome 17, so only chromosome 17 is encoded; with a reference of the whole genome, you’d put chr17 in Only these contigs.

Press Run. Python reads chromosome 17’s 83 million bases from the web (about 23 MB), applies each of the 206 records base by base, and writes ~/genomes/HG002_TP53.gpxil.tif: about 23 MB, almost all of it the reference plane. It takes about a minute on a desktop computer, longer on a phone, and about half a gigabyte of memory, because the encoder holds the whole chromosome’s planes while it works (the same command takes about 12 seconds on a computer’s own Python). The note under the result says how many contigs and bases it wrote.

The settings you’ll most often change:

Planes from the VCF
The genotype and flags planes (gt, flags) are all that sequences, pictures and VCF need. A VCF’s genotype qualities, read depths and phase sets can go in too (gq, dp, ps), but they take as much memory again.
Sex chromosomes
For a man’s VCF, XY gives chromosomes X and Y one copy outside the pseudo-autosomal regions, so his second haplotype is ABSENT there rather than a copy of the first.
Sample
The VCF column to encode, if it has several.

Make a gpxil file describes every setting.

4 · Check it and look at it

In the Viewer, the 150,000 bases around TP53 are faded reference where they were called with confidence, with HG002’s variants in orange and red, and grey (unknown) between and around the stretches of the BED file – as is the whole of the rest of the chromosome.

5 · The same, without the reference

The reference plane takes up nearly all of the file, and it is the same for everyone. Draw a gene, a region or a chromosome

A gpxil file is already a picture: each base is a pixel. Drawing a region means choosing which bases, how to colour them and how to lay them out. This walkthrough draws HG002’s TP53 in each of the four views, a satellite repeat that appears only when the rows are the right width, and a whole chromosome, the mitochondrion’s.

1 · Find the region in the Viewer

The Viewer is the quickest way to find a region worth drawing. Type a region such as chr17:7,661,779-7,687,546 (TP53), move along with the arrows, and zoom with + and −. Under the picture, the Viewer gives the gpxil render command that draws what you see as a file, and Save the picture saves the view as it is.

Regions count from 1 and include both ends, as in a genome browser: chr17:7,661,779-7,687,546 is 25,768 bases. A contig’s name alone means all of it.

2 · Draw it

Draw a region as a picture writes the region as a PNG (or a TIFF). For a region the size of a gene, it suggests 256 bases a row and 4 pixels a base, so each base is a square you can see.

3 · The four views

ShowWhat each pixel is
referencethe reference’s base, in the palette’s colours. Bases in soft-masked repeats (lower case in the reference) are paler, an unknown base (N) is near-black, in the classic colours, and a gap is paper.
genotypethe person’s two bases at once: where both copies agree, their base’s colour; where they differ, a mix of the two colours. A base deleted from both copies is paper.
haplotypesthe two copies separately, in two rows of pixels for each row of bases: the first haplotype above the second. With Mark where insertions are, a base that an insertion follows is magenta.
variantsthe reference, faded, with the person’s variants on top: heterozygous orange, homozygous red, a deletion dark, a base an insertion follows green, no call grey, a complex variant purple.

The Colours are one of gpxil’s palettes: classic (A red, C blue, G green, T yellow), okabe-ito, whose colours people with colour-blindness can tell apart, gpxi, the greys of Albrecht-Buehler’s original genome pixel images, and process, the four printing inks. The palettes gives their exact colours.

4 · The width of the rows

The width of the rows changes nothing in the data, only how it is laid out, but it can change what you see. A repeat whose unit is as long as a row lines up in columns. Near the middle of chromosome 17 lies alpha satellite, the repeat that makes up centromeres, in units of 171 bases. At 171 bases a row it shows as vertical stripes; at 200 it looks like noise.

In the form, set Bases per row to 171, then to 200, and compare the two pictures. This is how Albrecht-Buehler found repeats by eye: by wrapping a sequence at the width of its period.

5 · A Hilbert curve

In rows, bases that are next to each other in the genome can end up far apart in the picture: the last base of one row and the first of the next. A Hilbert curve layout folds the sequence into a square so that neighbours stay neighbours, and any stretch of the sequence is a compact blob. A gene shows as a patch rather than a band.

(Choose a Hilbert curve under Layout.) TP53’s 25,768 bases fill a square of 256 by 256 pixels, with room to spare.

6 · A whole chromosome

The mitochondrial chromosome is small enough to draw whole: 16,569 bases, its name alone as the region.

In the browser, a picture may have up to 25 million bases and 64 million pixels: a region of any chromosome, but not a large chromosome in one go (chromosome 21, the shortest autosome, has 46.7 million bases). To see a whole chromosome at one dot a base, print it as a book (Print a chromosome as a book); on your own computer, gpxil render has no such limit.

7 · For print

A PNG is for the screen. For print, choose TIFF in CMYK under Picture: each base’s colour is then given directly in ink, in the palette’s own CMYK values, rather than converted from screen colours. Give the Dots per inch you will print at, and with one pixel a base, each base is one printed dot.

See a person’s own version of a protein

A gpxil file holds both copies of each of a person’s chromosomes, base by base, so their own versions of a gene can be spelt out, spliced into transcripts and translated into proteins. This walkthrough does it for TP53 in HG002, whose two copies of the TP53 protein both differ from the reference’s at amino acid 72. The results are pxil files: pictures with one pixel for each base or amino acid, which hold the sequence exactly.

1 · The gene and its transcripts

TP53 lies on the minus strand of chromosome 17, at chr17:7,661,779-7,687,546. Ensembl knows 40 transcripts of it. Its canonical transcript, TP53-201 (ENST00000269305), which is also the MANE Select transcript, has 11 exons and makes the 393 amino acids of the protein ENSP00000269305. To list a gene’s transcripts, tick Only list each gene’s transcripts in the tool, or use --list in the terminal (below).

2 · Make the pictures

Genes, transcripts and proteins as pxil pictures makes, for each transcript you choose, a picture of the gene’s sequence, of the spliced transcript and of the protein. From says whose: the reference, either of the person’s haplotypes, or all three, so you can compare them.

It writes nine files into ~/results/pxil/TP53 – three pictures each from the reference and from HG002’s two haplotypes – and says how each differs from the reference’s:

TP53_ENSG00000141510_HG002-hap1.gene.pxil.png (25,757 bases): 39 changes from the reference
TP53-201_ENST00000269305_HG002-hap1.transcript.pxil.png (2,511 bases): 2 changes from the reference in its exons
TP53-201_ENSP00000269305_HG002-hap1.protein.pxil.png (394 amino acids): differs from the reference: P72R

HG002’s copies of the gene differ from the reference at dozens of places, almost all of them in introns, which are spliced out. Two changes fall in the transcript’s exons. One changes the protein: proline 72 becomes arginine. The other, one T fewer in a run of Ts, is in the 3′ untranslated region, after the stop codon, which is why the transcript is a base shorter. The protein has 394 residues: 393 amino acids and the stop codon, written *.

3 · Look at a picture

Open a protein picture in the Files tab. It is an ordinary PNG, 20 pixels a row for 394 residues, each amino acid in its own colour, and the Files tab shows it large, with what it says about itself – the protein, its transcript and gene, its chromosome, and the note differs from the reference: P72R – and its sequence underneath. Its name says whose it is: _HG002-hap1. Amino acid 72 is in the fourth row, twelfth from the left. Point at it: in HG002’s picture the line under it says amino acid 72: R (arginine), in the reference’s amino acid 72: P (proline), and the two pixels have different colours.

The colours are only for the eye. What matters is the pixel values: each one is a residue’s place in the file’s alphabet, so the sequence can be read back exactly, by any program that reads PNG – the Files tab reads it in the page, without Python. Copy the sequence puts it on the clipboard. pxil pictures of sequences explains the format.

4 · The sequences back, as FASTA

pxil pictures → FASTA reads the sequences back from the pictures. Choose the three protein pictures, and the FASTA file has the reference’s TP53 and HG002’s two, which you can compare in any alignment program.

Tick Their metadata (JSON) instead of their sequences to see what each picture says about itself: its gene, transcript and protein IDs, its exons and coding region, the sample and haplotype it came from, and its notes, such as differs from the reference: P72R.

5 · How the sequences are made

  • A haplotype’s sequence is the reference with the person’s variants applied: substitutions replace bases, deletions remove them, insertions are put after their anchor base, and bases whose state isn’t known become N.
  • The transcript is the haplotype’s sequence over each exon, joined, and read 5′ to 3′: for a gene on the minus strand, such as TP53, that means reverse-complemented.
  • The protein is translated from the annotated start codon to the first stop codon. A frameshift is followed into the 3′ untranslated region, and a protein whose stop codon is lost runs to the end of the transcript (and the file says so).
  • Selenocysteines (TGA read as U) are kept where Ensembl annotates them, and genes on the mitochondrion use the vertebrate mitochondrial code.

6 · Other genes, other transcripts

  • Genes takes several symbols or Ensembl IDs, separated by spaces. HG002’s example file holds only chromosome 17, so its genes must be there (BRCA1 is, and HG002’s copies of its protein are the same as the reference’s).
  • Any gene of GRCh38 can be drawn from the reference itself, from its chromosome in /data/grch38: CFTR from /data/grch38/chr7.gpxil.tif, say.
  • Transcripts: the canonical one (the default), the MANE transcripts, every protein-coding one, or every one.
  • Genes from: by default, the Gpxil browser’s gene files, every transcript of Ensembl release 116 on GRCh38, read from the web a gene at a time. For another annotation, or another assembly, give a GTF file, such as /data/examples/TP53.gtf, TP53’s lines of Ensembl 116’s GTF, which also works without the web.

Get sequences and variants back out

Other programs read FASTA and VCF, not gpxil. This walkthrough writes a person’s two versions of a region as FASTA, their genotype as a single sequence of IUPAC codes, and their variants as a VCF file – and then turns that VCF back into a gpxil file, to show that nothing was lost on the way.

1 · A person’s two haplotypes

Sequences as FASTA writes the sequence of either haplotype over a region. It is the reference with the person’s variants applied: substitutions replace bases, deletions remove them, insertions are put after their anchor base, and bases that weren’t called become N. So a haplotype’s sequence can be shorter or longer than the region. Lower case, for the reference’s soft-masked repeats, is kept.

TP53 is 25,768 bases in the reference; HG002’s first copy of it is 25,757 bases, his second 25,767.

2 · The genotype as one sequence

the genotype, in IUPAC codes writes one sequence as long as the reference, with each base where the two haplotypes differ as the IUPAC code of both: R for A and G, Y for C and T, and so on. It’s the form many programs that expect one sequence for a person can read. A base deleted from one haplotype shows the other’s base; one not called is N.

For the worked example, whose reference is ACGTACGTac, the two haplotypes are ACGTGTGGnc and ATGTACGTGGgc, and the genotype is AYGTACGTNc: Y where one haplotype has C and the other T.

3 · The variants, as VCF

Variants as VCF writes a VCF record for each place where either haplotype differs from the reference, with the genotype phased (|) where the file says it was, and with the genotype quality, read depth and phase set where the file has them. A record that didn’t pass its filters is marked gpxil_filtered.

For TP53 it writes 21 variants and 9 no-call blocks: records with ALT <*>, an END and genotype ./., for the stretches that weren’t called with confidence. They let a program tell “not called” from “the same as the reference”; untick Write no-call blocks to leave them out. The VCF of a region has exactly the records that the VCF of the whole chromosome has there, so a deletion that starts just before the region is written whole.

The records are equivalent to the ones the file was made from, not copies of them: each says what the two haplotypes carry over a stretch of the reference, and neighbouring changes may be joined into one record. IDs, QUAL, INFO and the other FORMAT fields of the original aren’t kept in a gpxil file, so they aren’t written.

4 · And back again

Encoding the exported VCF again, with the gpxil file itself as the reference, gives the same planes. The example workflow Back to FASTA and VCF, and round again does all of this in one go – both haplotypes, the VCF, the new gpxil file, and a check of it.

A book of a person is their genome

A book printed at one dot a base holds the genome in printed form: scanned at a high enough resolution, it can be read back. A book made from a person’s gpxil file – in the genotype, haplotypes or variants views – is as identifying as the file itself, and says things about their relatives too. Treat it with the same care. A book of the reference alone identifies no one.

4 · Printing it

Print at the PDF’s actual size (“100 %” or “actual size”, not “fit to page”), on the paper you chose, at the printer’s full resolution. The colours are given in device CMYK, so ask the print shop to proof them with their printer’s colour profile. Every base is a square dot with smoothing turned off, so the PDF stays sharp at any zoom.

The same in the terminal

gpxil book /data/examples/HG002_chr17.gpxil.tif -o ~/results/HG002_chr17_proof.pdf --contigs chr17 --max-pages 5

Work with a gpxil file pixel by pixel, in Python

In Python, each plane of a gpxil file is a NumPy array with one number for each base, so the questions you ask of a genome – where does this person differ from the reference, and how; what wasn’t called; how do their two copies differ – are a line or two of array arithmetic. This walkthrough asks them of HG002’s TP53, and of his whole chromosome 17, and ends by writing a gpxil file with a plane of its own.

Each box below is a cell to run in the Notebook tab: press Add to notebook on it, or open the starting notebook, which goes through the same ground. Every box starts by opening the file, so you can run any of them on its own.

1 · Open a file

GpxilFile opens a gpxil file: a path, or the address of one on the web. It reads only the metadata; each contig is an object that knows its name, its length, its layout width and its planes.

from gpxiltools import GpxilFile

g = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")
print(g.sample_id, g.contigs)
c = g["chr17"]
print(f"{c.length:,} bases, {c.width} a row, {c.rows:,} rows; planes {c.planes}")

2 · Read a region of each plane

c.read(plane, start, end) gives a plane’s values over a region as a NumPy array. Positions in Python count from 0 and the end isn’t included, so TP53, chr17:7,661,779-7,687,546 as a genome browser writes it, is start=7_661_778, end=7_687_546. Only the strips of the file that hold the region are read and decompressed: a few hundred kilobytes for a gene, however big the file.

from gpxiltools import GpxilFile
from gpxiltools import codes as C

c = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")["chr17"]
start, end = 7_661_778, 7_687_546          # TP53
ref = c.read("ref", start, end)
gt = c.read("gt", start, end)
flags = c.read("flags", start, end)
print(ref.dtype, ref.shape, gt.dtype, flags.dtype)
print(ref[:12])                            # codes …
print(C.ref_to_ascii(ref[:60]).decode())   # … as letters (lower case: soft-masked)
print(c.sequence(start, start + 60))       # the same, in one step

3 · Decode the codes

Every value is a code (The codes). A ref value is a base as a set of bits – A 1, C 2, G 4, T 8 – plus 16 for a soft-masked base. A gt value holds two states, one in each half of the byte: the high four bits for haplotype 1, the low four for haplotype 2. A state is 0 for the reference’s base, or the bits of another base, or one of the special states: 10 ABSENT, 12 COMPLEX, 13 DEL (deleted), 15 UNKNOWN. HG002’s variant at chr17:7,676,154, which changes TP53’s amino acid 72:

from gpxiltools import GpxilFile
from gpxiltools import codes as C

c = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")["chr17"]
start, end = 7_661_778, 7_687_546
ref, gt, flags = (c.read(p, start, end) for p in ("ref", "gt", "flags"))
i = 7_676_154 - 1 - start                  # chr17:7,676,154 in the region
print("reference", C.ref_to_ascii(ref[i:i + 1]).decode())
print("gt", hex(gt[i]), "=", C.describe_gt_byte(int(gt[i])))
print("haplotype 1:", C.hap1(gt)[i], " haplotype 2:", C.hap2(gt)[i])
print("flags", flags[i], [name for bit, name in C.FLAG_NAMES.items() if flags[i] & bit])

The reference has G; the gt value 0x22 is C on both haplotypes (2 is C); the flag is VARIANT_SITE, “a call covers this base”, without PHASED. The quality planes say how sure the call is: c.read("gq", …) and c.read("dp", …) are 254 here, their highest value (255 means not known).

4 · Find the variants

Whole arrays at once: split gt into its two haplotypes, and a base is heterozygous where one haplotype carries another base and the other the reference’s, homozygous where both carry the same other base.

import numpy as np
from gpxiltools import GpxilFile
from gpxiltools import codes as C

c = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")["chr17"]
start, end = 7_661_778, 7_687_546
gt, flags = c.read("gt", start, end), c.read("flags", start, end)
h1, h2 = C.hap1(gt), C.hap2(gt)
sub1, sub2 = np.isin(h1, C.HAP_SUB_CODES), np.isin(h2, C.HAP_SUB_CODES)
het = (sub1 & (h2 == C.HAP_REF)) | (sub2 & (h1 == C.HAP_REF)) | (sub1 & sub2 & (h1 != h2))
hom = sub1 & sub2 & (h1 == h2)
deleted = (h1 == C.HAP_DEL) | (h2 == C.HAP_DEL)
inserted = (flags & (C.FLAG_INS1 | C.FLAG_INS2)) != 0
unknown = (h1 == C.HAP_UNKNOWN) | (h2 == C.HAP_UNKNOWN)
print("heterozygous", het.sum(), "homozygous", hom.sum(), "deleted bases", deleted.sum(),
      "insertions after", inserted.sum(), "not called", unknown.sum())
print("homozygous at", (np.nonzero(hom)[0] + start + 1).tolist())   # back to 1-based positions

In TP53, HG002 has 3 heterozygous and 11 homozygous substitutions, 27 deleted bases and 2 insertions, and 970 bases weren’t called. np.nonzero gives where in the region; adding start + 1 turns those back into positions as a genome browser writes them.

5 · A whole chromosome, a piece at a time

The same counts over the whole of chromosome 17. Reading it in pieces of 8 million bases keeps the memory needed small – 8 MB for each plane read, and a few times that for the arrays worked out from it – however long the chromosome. This is how to go through a whole genome in the browser (A whole genome without running out of memory).

import numpy as np
from gpxiltools import GpxilFile
from gpxiltools import codes as C

c = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")["chr17"]
step = 8_388_608
het = hom = unknown = 0
for a in range(0, c.length, step):
    gt = c.read("gt", a, min(a + step, c.length))
    h1, h2 = C.hap1(gt), C.hap2(gt)
    sub1, sub2 = np.isin(h1, C.HAP_SUB_CODES), np.isin(h2, C.HAP_SUB_CODES)
    het += int(((sub1 & (h2 == C.HAP_REF)) | (sub2 & (h1 == C.HAP_REF)) | (sub1 & sub2 & (h1 != h2))).sum())
    hom += int((sub1 & sub2 & (h1 == h2)).sum())
    unknown += int(((h1 == C.HAP_UNKNOWN) & (h2 == C.HAP_UNKNOWN)).sum())
print(f"{het:,} heterozygous and {hom:,} homozygous substitutions")
print(f"{unknown:,} of {c.length:,} bases not called ({unknown / c.length:.1%})")

HG002 has 54,935 heterozygous and 34,713 homozygous substitutions on chromosome 17, and 13.1 % of it wasn’t called with confidence by the benchmark: mostly centromeres, segmental duplications and other hard places. gpxil stats makes these counts, and more – insertions, deletions, Ti/Tv, phasing, quality – in one go, in the same way (Count what a file holds).

6 · Compare the two haplotypes

Where do HG002’s two copies of TP53 differ from each other? Where their states differ. With phased calls (PHASED in flags), haplotype 1 is one parent’s copy throughout a phase set (the ps plane); HG002’s calls here aren’t phased, so it only says which bases are heterozygous. The sequences themselves come from haplotype_sequence, which applies the variants to the reference, insertions and deletions included.

import numpy as np
from gpxiltools import GpxilFile
from gpxiltools import codes as C
from gpxiltools.export import haplotype_sequence

c = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")["chr17"]
start, end = 7_661_778, 7_687_546
gt = c.read("gt", start, end)
differ = C.hap1(gt) != C.hap2(gt)
print(differ.sum(), "bases where the two haplotypes differ:", (np.nonzero(differ)[0] + start + 1).tolist())
s1 = haplotype_sequence(c, 1, start, end).decode()
s2 = haplotype_sequence(c, 2, start, end).decode()
print(len(s1), len(s2), "bases, against", end - start, "in the reference")

9 · A gpxil file of your own, with a plane of your own

GpxilWriter writes gpxil files: give it each contig’s planes as arrays. Besides the standard planes, a file can carry planes of your own, whose names start with x-. Here the mitochondrion’s reference is copied from GRCh38, with a new plane, x-gc: the percentage of G and C in the 101 bases around each base. The checksums are copied too, so the new file can prove that its reference is GRCh38’s.

import numpy as np
from gpxiltools import GpxilFile, GpxilWriter
from gpxiltools import codes as C
from gpxiltools.validate import validate

with GpxilFile("/data/grch38/chrM.gpxil.tif") as g:
    c = g["chrM"]
    ref = c.read("ref")
    checksums = {k: c.entry[k] for k in ("md5", "refget")}
    reference = g.metadata["reference"]
base = C.ref_base_nibble(ref)                                   # without the soft-mask bit
gc = np.isin(base, (C.BASE_G, C.BASE_C)).astype(float)
gc_101 = np.round(np.convolve(gc, np.ones(101) / 101, mode="same") * 100).astype(np.uint8)
with GpxilWriter("/home/user/genomes/chrM_gc.gpxil.tif", width=128, reference=reference) as w:
    w.add_contig("chrM", {"ref": ref, "x-gc": gc_101}, **checksums)
print(validate("/home/user/genomes/chrM_gc.gpxil.tif").ok, GpxilFile("/home/user/genomes/chrM_gc.gpxil.tif")["chrM"].planes)

A reader that doesn’t know a plane of your own ignores it, so the file is still a gpxil file to every tool, and gpxil validate passes it. A plane with a sample’s genotype needs GpxilWriter(…, sample={"id": …}) and a flags plane beside its gt; gpxil encode makes those from a VCF.

A whole genome without running out of memory

A human genome is 3.1 billion bases. As one byte a base, a single plane of it is 3.1 GB in memory, more than Python in a browser can use, although the file that holds it is under 1 GB. Yet the studio opens a whole genome at once, because it never reads more of a file than it needs. This walkthrough shows how, and how to write your own code the same way.

1 · Read regions, not files

Each plane of a gpxil file is stored in strips of whole rows: 32 rows of 8,192 bases, 262,144 bases a strip, in a file made with the default layout. Reading a region decompresses only the strips that hold it. A gene is one strip or two, so reading it costs the same in a file of one chromosome as in a file of the whole genome.

The studio adds one more step. A file of 8 MB or more is never copied into Python’s memory: Python reads it where the browser keeps it, or from the web, a piece at a time. The chromosomes of GRCh38 in /data/grch38 are read from the Gpxil browser’s site like this, a megabyte at a time, as they’re needed. And the Viewer and the Files tab read gpxil files without Python at all.

2 · A chromosome, a piece at a time

To go through a whole chromosome, read it in pieces and keep only what you work out from each. This finds the GC content of each megabase of chromosome 21, read from the web: at any moment, Python holds one megabase.

import numpy as np
from gpxiltools import GpxilFile
from gpxiltools import codes as C

c = GpxilFile("/data/grch38/chr21.gpxil.tif")["chr21"]
step = 1_000_000
gc = []
for a in range(0, c.length, step):
    base = C.ref_base_nibble(c.read("ref", a, min(a + step, c.length)))
    acgt = np.isin(base, (C.BASE_A, C.BASE_C, C.BASE_G, C.BASE_T)).sum()
    gc.append(np.isin(base, (C.BASE_G, C.BASE_C)).sum() / acgt if acgt else np.nan)
gc = np.array(gc)
print(f"{c.length:,} bases in {gc.size} pieces, {np.isnan(gc).sum()} of them all N")
print(f"GC from {np.nanmin(gc):.1%} to {np.nanmax(gc):.1%}, highest in megabase {np.nanargmax(gc) + 1}")

Chromosome 21’s first five megabases are all N – the short arm, which GRCh38 doesn’t spell out – and its GC content runs from 34.6 % to 53.0 %, highest near the end of its long arm. A loop over all the chromosomes of a genome works the same way, contig by contig: for c in g:. gpxil stats goes through a file like this to count what it holds (section 4).

3 · Files without the reference, which borrow it

A person’s genome as a gpxil file is mostly their reference: the same bases for everyone. Written without the reference plane (gpxil encode --no-ref), it is a small fraction of the size, and names its reference by checksums. Open it with the reference, and gpxiltools reads just the region you ask for from the reference, after checking that its checksums match. The Viewer does the same by itself for a file made on GRCh38.

from gpxiltools import GpxilFile
from gpxiltools.encode import encode
from gpxiltools.export import haplotype_sequence

encode("/data/grch38/chr17.gpxil.tif", "/home/user/genomes/HG002_TP53.noref.gpxil.tif",
       vcf="/data/examples/HG002_TP53.vcf", callable_bed="/data/examples/HG002_TP53.bed",
       planes=["gt", "flags"], include_ref=False)
with GpxilFile("/home/user/genomes/HG002_TP53.noref.gpxil.tif", reference="/data/grch38/chr17.gpxil.tif") as g:
    c = g["chr17"]
    print(c.planes, "plus the borrowed reference:", c.has("ref"))
    print(haplotype_sequence(c, 1, 7_676_100, 7_676_200).decode())

4 · A working copy, and what it holds

To work on part of a big file, make a working copy of it: gpxil subset copies the contigs you choose, and the planes you choose, into a new file. It copies the pages’ strips as they are stored, without decoding them, so it takes little memory and little time, even from a whole genome or a file on the web. Leaving out the reference plane makes the copy about a hundred times smaller: HG002’s chromosome 17 goes from 24.6 MB to 1.9 MB, and the Viewer borrows the reference from GRCh38 as before.

gpxil subset /data/examples/HG002_chr17.gpxil.tif chr17 --no-ref -o ~/genomes/HG002_chr17.noref.gpxil.tif
gpxil stats ~/genomes/HG002_chr17.noref.gpxil.tif

gpxil stats then counts what the copy holds, a piece at a time: 86.9 % of chromosome 17 called, 54,935 heterozygous and 34,713 homozygous substitutions, and the insertions, deletions, phasing, quality and depth (Count what a file holds). Without the reference plane it counts all but the reference’s bases and Ti/Tv; give it --reference /data/grch38/chr17.gpxil.tif for those. The Viewer counts the same for the region in view, under its key.

5 · What uses memory, and what doesn’t

  • Doesn’t: opening a file, its metadata, the Viewer, the Files tab, reading a region, a loop over pieces, gpxil info, gpxil vcf and gpxil fasta (which write as they go), gpxil validate and gpxil stats (which read a piece at a time), gpxil subset (which copies a strip at a time).
  • Does: gpxil encode, which holds each contig’s planes whole while it works: about 6 bytes a base with the planes gt and flags, so half a gigabyte for chromosome 17 and about 1.5 GB for chromosome 1, more than a browser tab may have. In the browser, encode one chromosome at a time (Only these contigs, or --contigs), and the biggest chromosomes, or a whole genome, on your own computer (section 6). Also a whole plane read at once (c.read("gt") on chromosome 1 is 249 MB), and big pictures, which is why the tools stop at 25 million bases a picture in the browser.
  • Keep arrays small: uint8 as they come, not converted to 64-bit numbers. del big arrays you’ve finished with, and if Python gets slow or stops with a MemoryError, restart it (the Notebook’s Restart, or the Python pill in the Tools tab): your files are safe, only Python’s variables are lost.

The Viewer

The Viewer shows a gpxil file as it is: one pixel, or a square of pixels, for each base, in rows that read from left to right and from top to bottom like a page of text. It reads only the part of the file it shows, straight from the file, without Python, so a whole genome opens at once – even one on the web.

File
Any gpxil file: yours, the examples, or a chromosome of the GRCh38 reference, read from the Gpxil browser. Add a file… puts one from your computer into ~/genomes and opens it; it stays in this browser.

Choose a contig, or type a region and press Go (or Enter): chr17:7,661,779-7,687,546, counting from 1 and including both ends, with or without the commas. A contig’s name alone means all of it, and one position, such as chr17:7676154, that base.
Show

Moving around

  • The arrow buttons move left and right by half the view; the magnifier zooms in to half as many bases, and − zooms out to twice as many.

  • Click the picture, and then the keys ← and → move by a quarter of the view, + and − zoom.

The views and their colours

Each view of the Viewer draws one or two planes of the file. The key under the picture names its colours; this page says what each one means. The first four views are exactly what gpxil render draws, pixel for pixel, in every palette, so a picture you like in the Viewer can be made as a file with the command under it.

Reference bases

The ref plane: each base in the palette’s colour (in the classic palette, A red, C blue, G green, T yellow). Bases in soft-masked repeats – lower case in the reference – are 45 % paler, except in the GPxI greys, which need all their levels. An ambiguous base is the mix of its bases’ colours. N, a base that isn’t known, has a colour that no base and no mix of bases has – near-black in the classic and Okabe–Ito colours, light blue in the GPxI greys, grey in the process inks – and is never paler. A gap, where there is no base, is the colour of paper.

Genotype

Each base as the person has it, both haplotypes at once, as one IUPAC code (The codes). Where the haplotypes agree, the base’s colour; where they differ, the mix of their two colours, so a heterozygous A/G base has the colour of R, half red and half green. A haplotype that wasn’t called, or that has a complex variant, counts as N, so its base is N’s colour: near-black in the classic colours. A base deleted from one haplotype shows the other haplotype’s base – so look for deletions in the next two views – and a base deleted from both is paper. Soft-masked bases stay paler, as in the reference.

The key lists the colours in view, with each heterozygous pair that is there – A and G, C and T and so on – and how many bases have it. In TP53, HG002 is heterozygous at only three bases, all of them A and G; in the 150,000 bases around it, every pair turns up. Some mixes are greys – in the classic colours, C and T mix to mid-grey – which is why N is near-black: a heterozygous base never looks like one that isn’t known. To see every heterozygous base in one colour, use the Variants view, where they are all orange.

Haplotypes

The two haplotypes separately, as two rows of pixels for each row of bases: haplotype 1 above, haplotype 2 below. Each pixel is that haplotype’s own base: a substitution in its new base’s colour, a deleted base paper (as is haplotype 2 where the person has only one copy), and a base that wasn’t called, or a complex variant, N’s colour (near-black in the classic colours). A heterozygous variant shows in one row and not the other; a homozygous one in both.

Variants

The quickest way to find variants: the reference is faded 80 % towards white, and the bases where the person differs from it are coloured by what kind of change it is.

ColourMeaning

The flags plane, one colour for the most telling flag of each base:

Genotype quality, read depth

The gq and dp planes, from white for 0 to deep blue for 99 or more (genotype quality) or 60 or more (read depth). Pink means the value isn’t known (255): a base that no call with that field covers.

Phase sets

The ps plane: each phase set in a colour of its own, and white where a base is in none. Within one phase set, haplotype 1 is the same parental copy throughout; between phase sets, it may not be.

The same in a file

The flags, quality, depth and phase-set views are the Viewer’s own: under them, a Python cell reads the plane’s values as a NumPy array, ready to add to the notebook. The codes describes the values behind every colour.

Workflows

A workflow is a set of the Tools tab’s tools joined together, so that each reads the files the ones before it wrote. Draw one in the editor, start from an example, or make one from the tools you’ve run; then run it on the same files again, or on new ones. They work like the workflows of Galaxy. The walkthrough takes you through one.

Inputs and steps

A workflow has inputs, the files it is given when it runs, and steps, each a tool. Each input says which kinds of file it takes – a gpxil file, a VCF, a reference (FASTA or gpxil), a BED file, a GTF file, pxil pictures – and can suggest a file, which the run page offers. An input can be optional, for a file a step can do without, such as a VCF’s BED file of callable regions.

Every tool can be a step except The palettes, which reads and writes nothing. What’s in a gpxil file and Check a gpxil file write no files, so nothing can follow them, but they say what they found in the run. Genes, transcripts and proteins as pxil pictures writes a set of files, which goes as a whole into a step that reads several, such as pxil pictures → FASTA.

The editor

  • Each step is a box, with its input files on the left and the files it writes on the right. Drag from a file’s dot to an input of another step to connect them; only files of a kind the input takes will connect, and never in a loop.
  • The + by a file lists the tools that can read it, and adds the one you choose, connected to it.
  • Click a box to see its settings beside the boxes. A step’s settings are its tool’s form, without the files, which come from the connections, and without where to save, which the run decides.
  • + Input file and + Add a step add boxes; Tidy arranges them in columns, inputs on the left. Changes are saved as you make them.
  • Click an empty part of the editor for the workflow’s own name and description, and its Checks: anything that stops it running, such as an input not connected.

Running

The run page asks for a file for each input, and for the folder for the results, by default ~/results/workflow/first input. Press Run it, and the steps run one after another, in an order in which each runs after the steps it reads from. Each step shows its state as it goes, and when it’s done, what it did; open it for its command, what it printed and the files it wrote. Check a gpxil file

gpxil validate checks a file against the gpxil specification, so that you – and anyone you send it to – can trust what it says. It reads the whole file a piece at a time, so it needs little memory even for a whole genome.

What it checks

  • The metadata, against the specification’s JSON schema: the keys a file must have, and the right kind of value in each.
  • The pages: that every contig has the pages its metadata names, in the right order, of the right size and type, with zero padding after the last base.
  • The codes: that every value of the ref, gt and flags planes is one the specification allows, that no haplotype claims as a variant the reference’s own base, and that phase sets are only on phased bases.
  • The sidecar: that it reads back, that each base flagged as followed by an insertion has exactly one inserted sequence and the other way round, and that every complex variant has its entry.
  • The checksums, if you ask: it spells out the reference plane’s bases and compares their MD5 and refget checksums with the metadata’s, which proves that the reference is the one the file names.

The form

The gpxil file
The file to check.
Recompute the sequences’ checksums
On by default. It reads every base of the reference plane: a few seconds for a chromosome kept here, and longer for one read from the web, which has to be downloaded (chromosome 1 is 67 MB). Untick it for a quick check.

What it says

Valid, with the number of contigs checked, or Not valid with a table of what is wrong. An error is something a reader can’t rely on: the file doesn’t follow the specification. A warning is worth knowing about but doesn’t make the file invalid. A file that isn’t gpxil, such as a TIFF picture, fails at once: its first page has no gpxil metadata. It writes no files.

In the terminal

gpxil validate /data/examples/worked-example.gpxil.tif
gpxil validate --no-digests /data/examples/HG002_chr17.gpxil.tif

It ends with exit status 0 for a valid file and 1 for one that isn’t, so a script can use it: gpxil validate FILE && echo fine.

    print("warning:", w)

Count what a file holds

gpxil stats counts what a gpxil file holds, for every contig or for the regions you give: how much of the genome was called, the person’s substitutions, insertions and deletions, how much is phased, and the quality and depth of the calls. It reads the planes a piece at a time, so a whole chromosome takes little memory and about ten seconds here (a few on your own computer), and the counts of regions add up to those of the whole.

What it counts

reference
The reference’s bases: A, C, G and T, with GC content (C and G over all four), N, gaps and soft-masked (repeat) bases.
called
Bases where every haplotype is known; not called, where neither is (UNKNOWN, as outside the regions called with confidence); partly called, where one is and one isn’t. A base with one copy (haplotype 2 ABSENT, as on chrX of a man) counts its one haplotype.
substitutions
Bases where a haplotype carries another base and none is unknown: homozygous where every haplotype carries the same one, heterozygous otherwise. Each base carried is a transition (A↔G, C↔T) or a transversion; their ratio, Ti/Tv, is about 2 for a whole human genome, and much lower in a call set with many errors.
insertions, deletions
A run of deleted bases on a haplotype is one deletion, homozygous when the other haplotype has the same run (or there is one copy); an insertion after a base likewise, by its inserted bases. Each comes with the bases inserted or deleted. An event belongs to the region it starts in, with all its bases.
complex
Complex variants (COMPLEX), such as inversions, by their entries in the sidecar.
phasing
The share of heterozygous substitutions that are phased, and the phase sets: how many, and their N50 and largest span, from their first to their last phased base.
genotype quality, read depth
The median, quartiles and mean of the gq and dp planes, over the bases that have a value.
filtered
Bases covered by a call that didn’t pass its filters.

A substitution is counted once at its base: a site where the two haplotypes carry two different other bases is one heterozygous substitution, with two bases towards Ti/Tv. Two neighbouring deletions on the same haplotype are one run, so one deletion. So the counts can differ slightly from those of tools that count VCF records.

The form

The gpxil file
Any gpxil file. One without a sample has only its reference counted.
Regions
One or more regions, separated by spaces: a contig, or CONTIG:START-END counting from 1. Leave it empty for every contig. With several, a table compares them, and the counts of all of them together follow.

Make a gpxil file (encode)

gpxil encode turns a reference genome, and one person’s variants from a VCF, into a gpxil file. Every base of the reference becomes a pixel of the ref plane, and every call in the VCF is written base by base into the gt and flags planes, as the specification sets out, so that any two programs that follow it make the same planes from the same VCF.

The form

The reference genome
A FASTA file (plain, gzip or bgzip), or a gpxil file with its reference plane, such as a chromosome of GRCh38 from /data/grch38. From a gpxil file, only the contigs you encode are read; a FASTA file is read a record at a time.
The person’s variants (VCF)
A VCF (or .vcf.gz) with the person’s genotypes, version 4.2 or later. Without one, the file holds the reference alone.
Sample
For a VCF of several people, the column to encode; by default, the first.
Regions called with confidence (BED)
Bases outside these regions are UNKNOWN – not called – rather than taken to be the reference. Give one whenever you have it: a VCF of variant sites says nothing about the bases it doesn’t list. A BED file with the same name as the VCF is chosen for you.
Only these contigs
Contigs of the reference, separated by commas, such as chr17. By default, all of the reference’s contigs; one with no calls in the VCF, and no callable regions, is stored as reference only.
Planes from the VCF
gt and flags (the default here), or all the VCF has: also its genotype qualities (gq), read depths (dp) and phase sets (ps), which take as much memory again.
Leave out the reference plane
A much smaller file, which names its reference by the checksums of its sequences. Reading its bases then needs the reference too.
Sex chromosomes
XY: chromosomes X and Y outside the pseudo-autosomal regions of GRCh38 have one copy, so haplotype 2 is ABSENT there. XX records the sex without changing anything.
The reference’s name
Such as GRCh38, recorded in the metadata. A gpxil file as the reference gives its own.
Bases per row of each page
The layout of the pictures, 8,192 by default. It changes nothing in the data – any reader can re-wrap a plane – but small rows make small strips, so a region reads quickly.
Compression
Deflate, which every TIFF reader supports, or none.
Colours stored for image viewers
The palette of the colour map stored with the ref plane, so that an ordinary image viewer shows the file in colour. It doesn’t change the data.
Save as
The new file, ~/genomes/name.gpxil.tif by default.

What it writes

One gpxil file, and a line saying how many contigs and bases it holds, how big it is and how long it took. Under that may come notes, such as VCF contigs that the reference doesn’t have (skipped), or calls that conflict with each other (the later one wins, and the metadata counts them). How a VCF becomes gpxil explains exactly how each kind of call is written.

It holds each contig’s planes whole while it works – about 6 bytes a base with the planes gt and flags – so the biggest contig sets the memory needed. HG002’s variants on chromosome 17 (83 million bases) take about half a gigabyte, and about a minute in the browser (12 seconds on a computer’s own Python); chromosome 1 (249 million bases) would need about 1.5 GB, more than a browser tab may have. So in the browser, encode one chromosome at a time, with Only these contigs, and encode the biggest chromosomes, or a whole genome, on your own computer (On your own computer).

Make a working copy (subset)

gpxil subset copies some contigs of a gpxil file, and if you like only some of its planes, into a new file: a working copy, such as one chromosome out of a whole genome. Each contig of a gpxil file stands on its own – its pages and its entry in the metadata – so nothing needs encoding again: the pages’ strips are copied as they are stored, without being decoded. It is quick, needs little memory, and works as well on a file you added to this browser, or one on the web.

What it is for

  • One chromosome out of a whole genome. A person’s whole genome is about 850 MB as gpxil; chromosome 17 is 25 MB of it. Make the copy on your own computer and add it here (On your own computer), or add the whole genome here: the copy reads only the pages it copies.
  • A smaller file. The reference plane is most of a file: without it, HG002’s chromosome 17 goes from 24.6 MB to 1.9 MB. The contigs keep the checksums of their reference, so any tool can be given it again (each tool has a field for it, and the Viewer borrows GRCh38’s from the Gpxil browser). Leaving out genotype quality and read depth (gq, dp) saves a little more.
  • The reference put back. A file written without its reference plane gets it again from a reference you give, which is checked against the checksums.
  • Another compression. A file made elsewhere with Zstandard, which the browser can’t read, encoded again with deflate (on a computer with the imagecodecs package).

The form

The gpxil file
Any gpxil file: yours, an example, or a chromosome of GRCh38.
Contigs
The contigs to copy, by name, separated by spaces or commas (chr17, or chr17 chr21); 17 finds chr17 too. Empty: all of them. The copy keeps them in the file’s order.
Planes
All the planes each contig has, or some of them: without genotype quality and read depth; the reference, genotype and flags only; or the reference only, without the sample. A plane a file doesn’t have is left out.
Leave out the reference plane
As gpxil encode --no-ref: a file about a hundred times smaller.
Put its reference plane back, from
Only for a file written without one: a FASTA file, or a gpxil file with its reference plane, such as a chromosome of GRCh38 from /data/grch38.
Compression
As it is (the default), so that the strips are copied without decoding, or encoded again.
Save as
A file name ending in .gpxil.tif, in ~/genomes unless you choose otherwise.

It won’t cut a contig: a file of part of a chromosome (TP53, say) needs the specification to say how its coordinates relate to the reference’s, which version 0.1 doesn’t. For a region, gpxil render, fasta, vcf and stats take one. Nor will it leave out the phase sets (ps) of a contig with more than one, because its phased calls would then read as one phase set.

What it writes

A gpxil file with the contigs and planes chosen, each contig with its entry in the metadata – its checksums, how it was encoded, how many records – and a record, subset, of the file it came from. It says how many contigs, bases and megabytes it wrote, and whether the strips were copied as stored. Check it, look at it in the Viewer, or count what it holds.

The palettes

A gpxil file holds codes, not colours. A palette turns them into colours when a picture is drawn: into screen colours (sRGB) for a PNG, or directly into ink (CMYK percentages) for print, so neither is converted from the other. gpxil palettes lists them.

classic
The colours of the original gpxil notebooks, and the default.
A red C blue G green T yellow N near-black
okabe-ito
Colours that people with any common colour-blindness can tell apart.
A bluish green C blue G orange T vermilion N near-black
gpxi
The grey levels of Albrecht-Buehler’s genome pixel images, after which gpxil is named.
A black C dark grey G white T light grey N pale blue
process
One pure printing ink for each base, which prints most faithfully.
A cyan C magenta G yellow T black N grey (35 % black)

Every palette also has a colour for “no base” (paper), and one for N (an unknown base) that no base or mix of bases has: near-black in classic and okabe-ito, whose mixes include greys, so that a heterozygous base never looks unknown. Neither is paler in a soft-masked repeat. The other codes are worked out from the four bases: an ambiguous base, or a heterozygous one in the genotype view, is the mean of its bases’ colours (in the process palette, the inks overprint), and a base in a soft-masked repeat is faded 45 % towards white (not in gpxi, whose greys need all their levels).

With the process palette, the code of a base is its ink: the four bits of a ref code, A, C, G and T, lay down cyan, magenta, yellow and black. A heterozygous A/G base prints cyan and yellow, green.

Variants as VCF

gpxil vcf writes the person in a gpxil file as a VCF again, so that any other genomics program can read their variants: a record for each place where either haplotype differs from the reference, and, if you like, a block for each stretch that wasn’t called.

The form

The gpxil file
A gpxil file with a sample; one written without its reference needs Its reference too, to spell out the alleles.
Regions
One or more regions, separated by spaces: a contig, or CONTIG:START-END counting from 1. Empty: every contig.
Write no-call blocks
On by default: each stretch of bases that weren’t called becomes a record with ALT <*>, an END and genotype ./., so that a program can tell “not called” from “the same as the reference”, and encoding the VCF again restores them.
Save as
The VCF file, in ~/results.

What it writes

A VCF (version 4.3) with one sample, named as in the gpxil file. Each record covers a stretch of the reference where either haplotype differs from it: REF is the reference over the stretch, and each haplotype’s sequence over it is an allele, so neighbouring changes may share a record. The genotype is phased (0|1) only where every called base of the record was phased. GQ, DP and PS are given where the file has those planes; a record over bases that failed their filters has FILTER gpxil_filtered; a complex variant keeps what the original VCF said of it in GPXIL_COMPLEX.

The VCF of a region has exactly the records that the whole contig’s VCF has there, so a deletion that starts just before the region is written whole; no-call blocks are cut at the region’s ends. IDs, QUAL, INFO and the other FORMAT fields of the original VCF aren’t in a gpxil file, so they aren’t written: the records are equivalent to the originals, not copies of them.

The gpxil format

A gpxil file stores a genome as pictures: one pixel a base, one picture for each chromosome and each kind of information, in an ordinary multi-page TIFF file. Any image software opens it as a picture of the genome; image libraries read its pictures as arrays of numbers; and it holds the reference and one person’s genotypes exactly, so they can be got back base for base. This page describes the format; the specification, version 0.1 (a draft), gives every rule.

Contigs and planes

A gpxil file has a list of contigs – chromosomes, the mitochondrion, unplaced scaffolds – and each contig has one or more planes: arrays with one value for each of its bases. Every plane is lined up with the reference, so the same pixel is the same position in every plane, and in every person’s file.

PlaneTypeWhat it holds
ref8-bitthe reference base, as an IUPAC code, and whether it is soft-masked (lower case: in a repeat)
gt8-bitthe person’s genotype: what each of their two haplotypes has at this base, four bits each
flags8-bitwhether the call here was phased, an insertion follows, the call was filtered, a call covers the base
gq, dp8-bitthe genotype quality and read depth of the call over the base, up to 254; 255 where there is none
ps32-bitthe phase set of a phased call; 0 where there is none
x-…8, 16 or 32 bits, or floating pointplanes of your own, such as x-methylation; readers ignore those they don’t know

A file holds at most one person. One without a person is a reference – ref planes only, like the chromosomes of GRCh38 in /data/grch38. A file can also leave the ref plane out and name its reference by checksums instead (below). A contig with a gt plane always has a flags plane too. The codes gives every value.

Layout: bases in rows

Each plane is a picture W pixels wide, filled like a page of text: base i, counting from 0, is in row i ÷ W and column i mod W, and the end of the last row is padded with zeros. The writer chooses the width and records it for each contig. gpxiltools uses 8,192, so chromosome 17’s 83,257,441 bases make pictures of 10,164 rows.

A plane is really a line of values, so any program can re-wrap it to another width without losing anything. A width equal to a repeat’s period lines the repeat up in columns. Other views, such as a book’s pages or a Hilbert curve, are made from the rows when they are drawn.

Pages: one picture for each plane

Every plane of every contig is one page of the TIFF file. The pages go contig by contig, in the order ref, gt, flags, gq, dp, ps, then planes of your own. Each page describes itself in JSON, such as {"gpxil": "0.1", "contig": "chr17", "plane": "gt", "length": 83257441}, and has a name for image viewers, such as chr17 gt. The first page also carries the metadata of the whole file.

The ref, gt and flags pages are palette pictures with a colour map, so that an ordinary image viewer shows them in colour. The colours are only for looking: no reader takes values from them. The other pages are greyscale.

Strips: reading a region

Each page is cut into strips of whole rows, and each strip is compressed on its own with Deflate (zlib), which every TIFF reader understands. gpxiltools makes strips of 256 KB before compression: 32 rows of 8,192 bases – 262,144 bases – for an 8-bit plane, and 8 rows for the 32-bit ps. To read a region, a reader works out the rows it covers and decompresses only their strips. So a gene costs the same to read from a file of one chromosome as from a file of the whole genome, and over the web only those strips need fetching (Big files and memory).

The sidecar: what doesn’t fit in a pixel

An insertion happens between two bases, so it has no pixel of its own. The flags plane marks the base it follows (INS1 or INS2, by haplotype), and the inserted bases go in the contig’s sidecar: a small table, compressed, in a private tag of the gt page (tag 65400). The sidecar also describes complex variants, such as inversions, which can’t be written base by base. This is the sidecar of the specification’s worked example – two Gs inserted after offset 7, on both haplotypes:

#gpxil-sidecar	0.1
offset	hap	kind	data
7	1	INS	GG
7	2	INS	GG

Programs built on libtiff, such as ImageMagick, warn about the unknown tag and otherwise ignore it.

The metadata

The first page’s description is a JSON object that says what the file holds. It must have gpxil (the version, "0.1"), layout (the default width), contigs and, in a file with a person, sample. Usually there too are reference (its name and source file), planes (their types and missing values), palette, generator, created and summary, the encoder’s totals. Each contig’s entry gives:

KeyWhat it holds
name, length, widththe contig’s name, its number of bases, and its layout width
pageswhich page holds each plane: {"ref": 0, "gt": 1, "flags": 2, …}
md5, refgetthe checksums of its reference sequence (below)
aliasesother names for it, such as 17 for chr17
ploidy1 if haplotype 2 is ABSENT everywhere, 2 if nowhere, otherwise "mixed"
encoding, callable_bases, sidecar_entries, phase_setswhat the encoder did (records applied, conflicts, mismatches with the reference …), the bases in the callable regions, the sidecar’s entries, and the phase sets

The sample object names the person (id, as in the VCF) and records what was applied: the VCF, the callable regions, the haploid regions and the sex. Readers ignore keys they don’t know, so writers can add their own.

Checksums: naming the reference

Each contig’s reference sequence has two checksums: its MD5, as in a SAM or CRAM header (@SQ M5), and its GA4GH refget identifier (SQ. and 32 characters). Both are worked out from the sequence in capital letters. They let a file written without its ref plane say exactly which reference it needs, and they let a reader check that a reference it is given is that one: gpxiltools refuses a reference whose checksums don’t match. For a FASTA file of plain IUPAC letters, they are the checksums other tools work out.

Why TIFF

  • Every image program opens it, so a gpxil file is a picture of the genome before it is anything else, and can be printed as one.
  • Image libraries – tifffile, Pillow, and those of image analysis – read its pages as arrays, so image operations become genome operations: the difference of two people’s gt planes, say, or a box filter over the G and C bits of ref for the GC content.
  • Strips give random access, and standard compression keeps files small: HG002’s chromosome 17, with all six planes, is 24.6 MB, and the whole of GRCh38 is 848.5 MB.
  • A file over 4 GB has to be a BigTIFF, which gpxiltools switches to by itself. A whole human genome with one person is under 1 GB.

The codes

A gpxil file holds numbers, not colours. This page gives the meaning of every number in the three main planes – the reference (ref), the genotype (gt) and the flags – and then works through the specification’s example, pixel by pixel.

ref: the reference base

One byte a base. Its low four bits are the base as a set of A, C, G and T, one bit each: A 1, C 2, G 4, T 8. So an ambiguity code is the sum of its bases – R, A or G, is 1 + 4 = 5 – and N, any base, is 15. These are the codes BAM files use for bases. 0 means no base (a gap). The next bit, 16, marks a soft-masked base: one written in lower case in the reference’s FASTA file, because it lies in a repeat.

CodeBaseStands forCodeBaseStands for
0-no base8TT
1AA9WA or T
2CC10YC or T
3MA or C11HA, C or T
4GG12KG or T
5RA or G13DA, G or T
6SC or G14BC, G or T
7VA, C or G15Nany base

Add 16 for a soft-masked base: a is 17, c 18, n 31. So a ref byte is 0 to 15, or 17 to 31.

gt: the genotype

One byte a base. Its high four bits are what haplotype 1 has there, its low four bits what haplotype 2 has: the byte is haplotype 1 × 16 + haplotype 2. In hexadecimal, that makes the first digit haplotype 1 and the second haplotype 2. Each haplotype’s state is relative to the reference base:

StateNameThe haplotype…
0REFhas the reference base
1, 2, 4, 8A, C, G, Thas this base instead (the same bits as in ref)
10 (hex A)ABSENTdoesn’t exist here: the person has one copy, as a man has of most of X and Y
12 (hex C)COMPLEXhas something that can’t be written base by base, described in the sidecar
13 (hex D)DELhas lost this base: it is deleted
15 (hex F)UNKNOWNwasn’t called, so isn’t known

The other values are reserved, and readers treat them as UNKNOWN. The special states’ letters are reminders: Absent, Complex, Deleted, and F – all four bits – for unknown, as N is all four bits in ref. A haplotype that has the reference base is always REF, never the base itself, so a base state always means a change.

Insertions aren’t states: they happen between bases. The base an insertion follows is flagged (below), and the inserted bases are in the sidecar (The gpxil format).

flags

One byte a base. Each bit is a flag, and a base can have several:

The other planes

gq and dp hold the genotype quality and read depth of the call over each base, from 0 to 254 (bigger values are stored as 254), and 255 where no call with that field covers the base. ps holds the phase set of the phased call over each base, as a 32-bit number, and 0 where the base isn’t phased.

How a VCF becomes gpxil, and back

A VCF lists a person’s variants as records; a gpxil file holds their genotype at every base. The specification fixes exactly how one becomes the other, so that any two encoders make the same planes from the same VCF. This page explains the rules, and why they are as they are. The codes gives the values they write.

1 · Before any call: what is assumed

  1. Every base of both haplotypes starts as REF, the reference.
  2. Given a BED file of callable regions – the regions called with confidence – both haplotypes are UNKNOWN outside them, and on a contig the BED file doesn’t mention, everywhere.
  3. Given haploid regions (--haploid, --haploid-contig, or --sex XY for X and Y outside the pseudo-autosomal regions of GRCh38), haplotype 2 is ABSENT inside them.

A VCF of variant sites says nothing about the bases it doesn’t list, so these are assumptions, and the metadata records which were made. They are also weak: any call overrides them. A contig on which the VCF has no records, and which no callable region touches, gets no gt plane at all, because saying that the person has the reference all along a chromosome nobody looked at would be wrong.

2 · A record becomes states, base by base

A record’s REF allele covers its span: from POS, for as many bases as REF has. Each haplotype takes the allele its genotype names, and that allele becomes a state at each base of the span:

  • 0, the REF allele: REF over the span. ., a missing allele: UNKNOWN.
  • A sequence allele: REF and ALT are trimmed of the bases they share, first at the end and then at the start, always keeping an indel’s anchor base. What is left lines up base by base. Where it differs, the haplotype has the ALT base: a substitution. Bases of REF left over are DEL. Bases of ALT left over are an insertion after the base before them: flagged (INS1, INS2) and kept in the sidecar.
  • *, a base deleted by another record: nothing is written, because the record that starts the deletion writes it.

Trimming the end first puts an indel as far left as the record allows, as VCF normalisation does, so calls inside repeats agree with their neighbours. In the worked example, chrT 4 TAC T 1|0 is trimmed to the anchor T and the deleted AC, so offsets 4 and 5 are DEL on haplotype 1; and chrT 8 T TGG 1|1 leaves GG inserted after offset 7 on both haplotypes.

3 · Symbolic alleles and blocks

  • <DEL> (and <DEL:ME> …): the bases after POS, up to END – from INFO/END, or else INFO/SVLEN – are DEL. POS is the padding base before them, so it stays REF.
  • <NON_REF>, <*> and <X> mean “any other allele”. A record with only these, as in a gVCF, is a reference block: its 0 alleles say REF up to END. A haplotype whose allele is one of them is UNKNOWN.
  • Anything else symbolic – an inversion, a duplication, a breakend: the haplotype is COMPLEX at the record’s first base, and the sidecar keeps the allele (REF=A;ALT=<INV>;END=…). What the haplotype has over the rest of the span can’t be written base by base, so those bases keep what they had.

4 · When calls overlap: which wins

Calls are applied in the order of the file, and each base remembers whether a call has spoken for it. A, C, G, T, DEL and COMPLEX are strong states: they say what the haplotype has. REF, UNKNOWN and ABSENT are weak.

  • A strong state always replaces what is there. If an earlier call had put a different strong state there, that is a conflict: the later call wins, and the metadata counts it.
  • A weak state is written only where no call has spoken yet.

So a record whose REF allele overlaps another record’s variant never undoes that variant, whatever the order of the records, and overlapping records that use * combine as they should. A multi-allelic site split into two records at one position (0/1 and 0/1) can’t be both, and shows up as conflicts.

5 · Genotypes, phase and the other fields

  • Haploid genotypes, such as 1: haplotype 2 is ABSENT over the span. Genotypes of more than two alleles are skipped, and counted.
  • Phased genotypes (0|1): PHASED is set, and haplotype 1 takes the first allele. In unphased ones (0/1), haplotype 1 also takes the first allele written, but the order means nothing – except that a * goes to the haplotype that has the deletion it stands for.
  • A missing genotype (./., or no GT): both haplotypes UNKNOWN, but only where no call has spoken, so it never erases a variant.
  • Flags add up over all the calls over a base: VARIANT_SITE over every call’s span, FILTERED where a call’s FILTER is neither PASS nor ..
  • GQ, DP and PS are written over the call’s span, GQ and DP up to 254. Where calls overlap, one that changed the base wins over one that didn’t.

6 · Checks

Every REF allele is checked against the reference, and mismatches are counted (ref_mismatches), so a VCF called against another reference shows up at once. VCF contigs are matched to the reference’s with or without chr, and MT with chrM, and the VCF’s name is kept as an alias. Records past the end of a contig are skipped, and counted. The counts are in each contig’s encoding metadata, and the encoder reports anything worth knowing.

7 · What is kept, and what isn’t

Kept exactly: the reference and its soft-masking; both haplotypes’ sequences – every substitution, deletion and insertion; phasing; haploid calls; no-calls; whether each call passed its filters; and the genotype quality, depth and phase set at each base.

Not kept: the records themselves – how the alleles were written, and where one record ended and the next began – IDs, QUAL, INFO, the other FORMAT fields, other samples, records on contigs the reference doesn’t have, and the bases of structural variants other than deletions, which are kept only as their COMPLEX entries.

8 · And back: gpxil to VCF

gpxil vcf writes a record for each event window. A substitution is a window of one base; a run of deleted bases takes the base before it as its anchor; an insertion takes the base it follows; and windows that share a base are merged. REF is the reference over the window, and each haplotype’s sequence over it is an allele. The genotype is phased only if every called base of the window was. FILTER is PASS, or gpxil_filtered where the bases failed their filters, since the filter’s own name isn’t kept. Runs of UNKNOWN become no-call blocks (ALT <*>, with END, and genotype ./.), so that encoding the VCF again restores them.

The records are equivalent to the originals – they spell the same two haplotypes – not copies of them: two records next to each other may come back as one, and an indel in a repeat may come back at another, equally correct place. Encoding the exported VCF gives the same haplotypes again.

pxil pictures of sequences

A pxil file holds one sequence – a gene, a transcript, a protein, or any other string of letters – as a picture: one pixel a residue, in rows like a page of text. It is an ordinary PNG, so anything that shows pictures shows it, and its pixels are the residues themselves, so the sequence comes back exactly. gpxil is for whole genomes; pxil is for single sequences, to look at, share and compare.

Pixels are residues

A pxil file is an 8-bit indexed-colour PNG. Each pixel’s value is a residue’s place in the file’s alphabet, a string of up to 256 letters stored with it: value i is the alphabet’s letter i. Residue i, counting from 0, is in row i ÷ width and column i mod width, and the pixels after the last residue are 0, which is kept for padding. The PNG’s palette gives each value a colour, so that the picture can be seen, but the colours mean nothing to a reader: change them, and the sequence is the same.

Two alphabets are standard:

AlphabetLettersColours, as gpxil2pxil and pxil make them
DNA, 32 letters-ACMGRSVTWYHKDBN-acmgrsvtwyhkdbnA red, C blue, G green, T yellow, N near-black, ambiguity codes mixed, and soft-masked (lower-case) bases paler
protein, 28 letters-ACDEFGHIKLMNPQRSTVWYUOBZJX*Taylor’s colours, one for each amino acid, and the stop codon * near black

The DNA alphabet is gpxil’s ref code (The codes), so a base’s pixel value is the same in both formats. Any other alphabet will do too, such as -ACGUN for RNA.

What it says about itself

The PNG has a text chunk (iTXt) named pxil, which holds JSON:

Keys

added by gpxil2pxilsample and haplotype, for a sequence made from a person; notes, such as differs from the reference: P72R; and a transcript’s biotype and tags (Ensembl canonical, MANE Select, MANE Plus Clinical)

A gene’s picture is its genomic sequence, introns included, 5′ to 3′. A transcript’s is spliced, 5′ to 3′, and written with T, as in Ensembl’s cDNA files. A protein’s runs from its N terminus to its C terminus, with the stop codon as *.

Names

pxil files are named label.kind.pxil.png, such as TP53-201_ENSP00000269305.protein.pxil.png, with the database’s ID in the label; gpxil2pxil adds the sample and haplotype, as in TP53-201_ENSP00000269305_HG002-hap1.protein.pxil.png. The name ends in .png so that computers treat the file as the picture it is. Readers go by the metadata, though, not the name.

Looking at one

Open a pxil file in the Files tab, and it is shown large, pixel by pixel, with its metadata – its kind, IDs and length, where it comes from, its notes – and its sequence, read from the pixels in the page, without Python. Point at a pixel, and the line under the picture names the residue and its number, such as amino acid 72: R (arginine). Copy the sequence puts the sequence on the clipboard, and As FASTA (pxil) opens pxil pictures → FASTA.

Big files and memory

A gpxil file of a chromosome is tens of megabytes, and of a whole genome nearly a gigabyte, while a browser tab has a few gigabytes at most – and Python less. So the studio never copies a big file whole: everything reads just the part it needs. This page explains how, what the limits are, and how to stay within them. A whole genome without running out of memory walks through it with examples.

The format makes it possible

Each plane of a gpxil file is stored in strips of 32 rows – 262,144 bases – each compressed on its own (The gpxil format). A reader opens a file by reading its metadata and the TIFF’s list of pages, a few kilobytes, and then decompresses only the strips a region needs. A gene is a strip or two, whether the file holds one chromosome or the whole genome.

Without Python: the Viewer and the Files tab

The Viewer and the Files tab read gpxil files themselves, in the page: the list of pages, then only the strips they show, decompressed by the browser. A file in your home folder is read where the browser keeps it, and a file on the web, such as GRCh38’s chromosomes, with HTTP range requests, which fetch just those bytes. So any gpxil file opens at once. The Viewer draws at most 4 million bases at a time.

Python: big files are lent, not copied

Python runs in a web worker – Pyodide, CPython compiled to WebAssembly – with a memory of its own. Small files are copied into it before a cell or a command runs, and the changes copied back afterwards. Files of 8 MB or more never are:

  • Your big files stay where the browser keeps them, and are lent to Python as files it reads a piece at a time.
  • The examples and the GRCh38 reference are read from the web a megabyte at a time, as Python asks for them, with HTTP range requests.
  • A big file that Python writes, such as a new gpxil file, is handed to the browser to keep when the command ends, and Python’s copy is freed.

gpxiltools reads only the strips of the region it is asked for, so gpxil info on chromosome 1 reads a few kilobytes, and a gene a few hundred. In the experiment that led to the studio, the whole genome as one file, 809 MB, opened in 72 MB of Python’s memory.

Working copies

To work on part of a big file, copy that part: gpxil subset makes a new gpxil file of the contigs you choose, and of the planes you choose, copying the pages’ strips as they are stored, so it takes about one strip of memory however big the file (Make a working copy). A chromosome of a whole genome is a few per cent of it, and without the reference plane a hundredth of that again. gpxil stats counts what a file holds a piece at a time in the same way (Count what a file holds).

Keeping your own code small

  • Read regions – c.read(plane, start, end) – not whole planes, and go through a chromosome in pieces: a strip (262,144 bases) or a megabase at a time.
  • Keep arrays as they come, 8-bit (uint8): chromosome 1’s plane as 64-bit numbers is 2 GB instead of 249 MB. Count with np.count_nonzero rather than building big arrays of results.
  • del big arrays you’ve finished with. Python’s memory doesn’t shrink, but what is freed is used again.
  • If Python stops with a MemoryError, or stops answering, restart it: Restart in the Notebook, or the Python pill in the Tools tab. Your files are safe; only Python’s variables are lost.

This counts HG002’s substitutions on chromosome 17, a strip at a time, so that it never holds more than a quarter of a megabyte of the plane:

import numpy as np
from gpxiltools import GpxilFile
from gpxiltools import codes as C

with GpxilFile("/data/examples/HG002_chr17.gpxil.tif") as g:
    c = g["chr17"]
    step = 32 * c.width                    # one strip: 262,144 bases
    het = hom = pieces = 0
    for a in range(0, c.length, step):
        gt = c.read("gt", a, min(a + step, c.length))
        h1, h2 = C.hap1(gt), C.hap2(gt)
        s1, s2 = np.isin(h1, C.HAP_SUB_CODES), np.isin(h2, C.HAP_SUB_CODES)
        hom += np.count_nonzero(s1 & s2 & (h1 == h2))
        het += np.count_nonzero((s1 & (h2 == C.HAP_REF)) | (s2 & (h1 == C.HAP_REF)) | (s1 & s2 & (h1 != h2)))
        pieces += 1
print(f"{het:,} heterozygous and {hom:,} homozygous substitutions, read in {pieces} pieces")

The browser’s storage

Your files are kept in the browser’s storage for the site (Where your files are kept). A single file bigger than 1 GB is there while the page is open but isn’t kept, so download it before you leave. The studio warns when your files come to more than 2,000 MB, and browsers limit what a site may keep, usually to a share of the free disk space. A whole genome with one person fits, but not many: for many people, keep files without the reference plane (--no-ref), a small fraction of the size, which borrow GRCh38 from the web when they need its bases.

Every tool and the Viewer can use them: as the reference to encode a VCF against, as a genome to look at or draw, or to make a gene’s pictures from.

What it is

  • The primary assembly of GRCh38, from Ensembl release 116 (Homo_sapiens.GRCh38.dna_sm.primary_assembly.fa.gz): chromosomes 1 to 22, X, Y and the mitochondrion, and 169 unplaced and unlocalised scaffolds, such as KI270728.1. There are no alternative haplotypes or patches.
  • Soft-masked: bases in repeats are lower case in Ensembl’s FASTA file, and marked as soft-masked in the ref plane, so the Viewer shows them paler.
  • The reference plane only, with no sample, written by gpxiltools 0.2.0 at 8,192 bases a row.
  • Named chr1 … chr22, chrX, chrY and chrM, with Ensembl’s names (1 … MT) as aliases, so a VCF that says 17 finds chr17. Each has its MD5 and refget checksums, which a file written without its reference plane is checked against.

Read from the web, a piece at a time

The files live on the Gpxil browser’s web site, comparativechrono.github.io/Gpxil-browser/data/grch38/. Nothing is downloaded whole: the Viewer and the Files tab fetch the strips they show, and Python reads a megabyte at a time, with HTTP range requests, as it needs to (Big files and memory). The first look at a chromosome takes a moment, and reading the reference needs a connection to the web.

A file of your own on GRCh38 written without its reference plane (--no-ref) borrows its bases from here: the Viewer does so by itself, the tools with Its reference, which they fill in for you, and gpxiltools with reference=. The checksums make sure it is the same reference.

Using it

  • To encode a VCF called on GRCh38: give the chromosome’s file to Make a gpxil file as the reference, a chromosome at a time (the walkthrough). Only the contigs encoded are read from it.
  • To look at: choose a chromosome in the Viewer, under GRCh38 reference.
  • To draw or print: gpxil render and gpxil book take any region of it.
  • For genes: gpxil2pxil makes any gene’s, transcript’s or protein’s picture from it, such as CFTR’s from chr7.gpxil.tif.
gpxil info /data/grch38/chr21.gpxil.tif
gpxil fasta /data/grch38/chr17.gpxil.tif --region chr17:7676101-7676200
gpxil render /data/grch38/chrM.gpxil.tif chrM -o ~/results/chrM.png --width 128 --scale 2

Its genes

The Gpxil browser also has the genes of Ensembl release 116 on GRCh38 – all 78,941 of them, and their 646,577 transcripts – with the canonical and MANE transcripts marked, and HGNC’s symbols, names and aliases. gpxil2pxil reads them a gene at a time when you name a gene (Genes, transcripts and proteins as pxil pictures). To work without the web, or with another annotation, give it a GTF file instead.

The whole genome in one file

For your own computer, the Gpxil browser offers the whole of GRCh38 as one gpxil file, GRCh38.gpxil.tif (848.5 MB), with its SHA-256 checksum beside it. Download it from the command line, check it, and use it like any other gpxil file:

Opening a file, with or without its reference

GpxilFile reads only the metadata when it opens a file, and a plane only where you ask for it. A file written without its reference plane (--no-ref) needs the reference to give its bases: a FASTA file, or a gpxil file of the reference such as those in /data/grch38. gpxiltools checks it against the checksums in the file, so the wrong reference can’t be used by mistake.

from gpxiltools import GpxilFile
from gpxiltools.encode import encode

with GpxilFile("/data/examples/HG002_chr17.gpxil.tif") as g:
    print(g.sample_id, g.metadata["reference"]["name"], g.contigs)
    c = g["chr17"]
    print(f"{c.length:,} bases, {c.width:,} a row; planes {c.planes}")
    print(c.sequence(7_676_148, 7_676_160), c.entry["md5"])

# the specification's worked example, written without its reference plane, then read with it
encode("/data/examples/worked-example.fa", "/home/user/genomes/worked-example.noref.gpxil.tif",
       vcf="/data/examples/worked-example.vcf", include_ref=False, width=4)
with GpxilFile("/home/user/genomes/worked-example.noref.gpxil.tif", reference="/data/examples/worked-example.fa") as g:
    c = g["chrT"]
    print(c.planes, c.has("ref"), c.sequence())

gpxil2pxil: genes, transcripts and proteins

Genes come from a GTF file, or from the Gpxil browser’s gene files (BrowserData(), Ensembl’s genes on GRCh38), which the studio reads from the web. Source gives a sequence from the reference (Source(g)) or from one of the sample’s haplotypes (Source(g, 1)), with the person’s variants in it.

from gpxiltools import GpxilFile
from gpxil2pxil import GTF, Source, make
from gpxil2pxil.sequence import protein_differences

g = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")
gene = GTF("/data/examples/TP53.gtf").find("TP53")
t = gene.canonical()                                   # the Ensembl canonical transcript, TP53-201
print(gene.id, len(gene.transcripts), "transcripts;", t.name, t.id, t.protein)
reference, hap1 = Source(g).protein(t), Source(g, 1).protein(t)
print(len(reference), "amino acids; haplotype 1:", protein_differences(reference, hap1))
for f in make(g, gene, kinds=["protein"], haplotypes=(None, 1, 2), out_dir="/home/user/results/pxil-python"):
    print(f.path, f.length, f.notes)

pxil files

A pxil file is a PNG picture of one sequence, so pxil.read needs nothing but Pillow. pxil.write makes one from any sequence: kind is gene, transcript, protein or sequence, and other keywords go into its metadata, such as sample and haplotype for a person’s own version of a sequence. pxil.fasta_name gives the name pxil gives it in a FASTA file.

import pxil
from gpxiltools import GpxilFile
from gpxil2pxil import GTF, Source

g = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")
t = GTF("/data/examples/TP53.gtf").find("TP53").canonical()
protein = Source(g, 1).protein(t)                       # TP53's protein from HG002's first haplotype
pxil.write("/home/user/results/TP53_HG002-hap1.pxil.png", protein, kind="protein", id=t.protein, name=t.name,
           sample=g.sample_id, haplotype=1, source="HG002_chr17.gpxil.tif")
sequence, meta = pxil.read("/home/user/results/TP53_HG002-hap1.pxil.png")
print(sequence == protein, meta["length"], meta["width"], sequence[60:80])
print(pxil.fasta_name(meta))

  • It’s bash: pipes, redirection, variables, loops, functions, $( ), here-documents and scripts (bash script.sh). ↑ and ↓ bring back earlier commands, Tab completes names, Ctrl+L clears the screen.
  • Ctrl+C stops a command: the program that’s running finishes, and the rest of the line or script is skipped. Press it again to stop the program at once. For gpxil, gpxil2pxil, pxil and python, that restarts Python, so a notebook’s variables are forgotten too.
  • The text programs – cat, head, tail, grep, sed, cut, sort, uniq, wc, tr, paste, diff, column, less and others – were written for this terminal after the GNU ones. NAME --help says which options each has. So were the file programs: ls, cp, mv, rm, mkdir, find, du, tree and the rest, and zip, unzip and tar.
  • python runs scripts, python -c "…" and python -m json.tool FILE, in the same Python as the notebooks. pip install NAME adds a package for this visit.
  • curl and wget download through the browser, from servers that let web pages read them: the Gpxil browser, Ensembl’s REST API, raw.githubusercontent.com, EBI and Zenodo, among others. You don’t need them for GRCh38, which is in /data/grch38 already.
  • open FILE shows a file in its tab, nano FILE edits it in the Files tab, and download FILE (or a folder, as a .zip) saves it to your computer.
  • Not here: background jobs (&), sudo, apt and ssh, and programs that aren’t in help’s list, such as bcftools and samtools. gpxil does much of their work on gpxil files: gpxil vcf --region cuts out a region as VCF, and gpxil fasta --which 1 spells out a haplotype.
Save pictures with -o, not >

The shell’s redirection (> and |) is for text. Pictures, PDFs and gpxil files are written properly only by the program itself, so give their names with -o, as every example here does.

Several at once

A loop does the same to many regions or files. These commands spell out the bases around TP53’s codon 72 from the reference and from each of HG002’s haplotypes, then make pictures of TP53’s protein from the reference and from both haplotypes, with the transcripts from a GTF file:

mkdir -p ~/results/P72
for which in ref 1 2; do
  gpxil fasta /data/examples/HG002_chr17.gpxil.tif --which $which --region chr17:7,676,140-7,676,170 -o ~/results/P72/P72.$which.fa
done
cat ~/results/P72/*.fa
gpxil2pxil /data/examples/HG002_chr17.gpxil.tif TP53 -a /data/examples/TP53.gtf --kinds protein --haplotypes all -o ~/results/P72
pxil ~/results/P72/*.pxil.png -o ~/results/P72/TP53-proteins.fa
grep '>' ~/results/P72/TP53-proteins.fa

gpxil2pxil says how each haplotype’s protein differs from the reference’s (P72R), and pxil puts the three proteins into one FASTA file, each named by its Ensembl ID and, for a haplotype, the person and the haplotype, ready for an alignment program. Without -a, gpxil2pxil takes Ensembl’s genes and transcripts from the Gpxil browser’s gene files, so any gene of GRCh38 can be named: gpxil2pxil /data/grch38/chr17.gpxil.tif BRCA1 --kinds protein -o ~/results.

The whole genome

The GRCh38 reference that the studio reads a chromosome at a time from the Gpxil browser is also one file of the whole genome, about 850 MB. Download it once, and give it to gpxil encode as the reference for a whole genome’s VCF:

curl -LO https://github.com/comparativechrono/Gpxil-browser/releases/download/grch38-ensembl116/GRCh38.gpxil.tif
gpxil encode GRCh38.gpxil.tif -v HG002.vcf.gz --callable HG002.callable.bed --sex XY --no-ref -o HG002.gpxil.tif
gpxil render HG002.gpxil.tif chr21 --mode variants -o chr21.png --reference GRCh38.gpxil.tif
gpxil stats HG002.gpxil.tif --reference GRCh38.gpxil.tif           # what it holds, chromosome by chromosome
gpxil subset HG002.gpxil.tif chr17 chr21 -o HG002_17_21.gpxil.tif   # a working copy to add to the studio

Encoding holds a chromosome’s planes in memory while it works, about 6 bytes a base, so the largest, chromosome 1, needs about 1.5 GB. HG002’s whole genome took 12 minutes and at most 2 GB of memory on an ordinary computer, and made a file of 888 MB with the reference plane. The Gpxil browser’s downloads also have each chromosome on its own, and a checksum to check the download with. Files without their reference plane (--no-ref) are a hundred times smaller; give the reference with --reference to the commands that need its bases (The GRCh38 reference).

To work on part of a whole genome here, make a working copy of the chromosomes you need with gpxil subset, which copies them without decoding, and add the copy with Add a file… in the Viewer or the Files tab (Make a working copy). The studio can also take the whole file and copy from it itself: it reads only the pages it copies.

Privacy

GpxilStudio is a web page that does all its work in your browser. Your genomes, VCF files and everything you make aren’t uploaded anywhere, and there’s no server behind the page that could see them.

Genomes are personal data

A gpxil file with a genotype plane is a person’s genome, and so is every faithful picture of it: a variants picture shows exactly where the person differs from the reference, and a book printed at one dot per base can be scanned and read back. A genome identifies the person, even without a name, and says things about their relatives, who haven’t agreed to anything (the gpxil specification, section 13). Use the studio as your institution’s rules on genetic data allow, and:

  • Treat gpxil files, their pictures and books, and pxil pictures of a person’s haplotypes with the same care as the VCF or CRAM file they came from. Leaving out the reference plane makes a file smaller, not less personal: it’s the genotype planes that identify the person.
  • Look at what a file says about the person before you share it. Its metadata keeps the sample’s ID and the names of the files it was made from (gpxil info --json), and a pxil file names the sample and the haplotype.
  • For pictures to show or publish, draw the reference only, or a region with nothing personal in it.
  • On a shared computer, download your work and use My files → Start afresh when you finish.

The examples are public: HG002’s genome was sequenced and released, with consent, for anyone to use as a benchmark, which is why the studio can show it.

When something goes wrong

These are the common problems, and what to do about each one.

Python and memory

“Python couldn’t start”
The first time you use it, the studio downloads Python (about 15 MB) from cdn.jsdelivr.net. If your network blocks that site, or you’re offline, the tools, the notebook and the programs can’t run, although the Viewer and the Files tab still work, because they read gpxil files in the page itself. Try again on another network. After the first time, the browser usually keeps a copy.
“Python stopped unexpectedly”, a MemoryError, or the page reloads by itself
Python ran out of memory. A browser tab has a few gigabytes at most, and some jobs need more: encoding holds about 6 bytes for each base of a chromosome, so chromosome 17 needs half a gigabyte and chromosome 1 about 1.5 GB, which may be too much; reading a whole chromosome’s planes at once in a notebook needs a byte a base for each plane. Reload the page: your files are kept. Then encode one chromosome at a time, read big regions in pieces, and do the biggest jobs on your own computer (A whole genome without running out of memory, Big files and memory, On your own computer).
A tool waits for a long time
A notebook cell may be running: the tools share the notebook’s Python, so they wait for it to finish. Stop the cell in the Notebook tab. The first tool of a visit also waits for Python to start, and a tool that reads the GRCh38 reference waits for its pieces to come from the web: encoding on chromosome 17 takes about a minute.

The reference

A file in /data/grch38 couldn’t be read
The studio reads the GRCh38 reference from the Gpxil browser’s site, comparativechrono.github.io, a piece at a time. Check that you’re online and that your network doesn’t block the site. Your own files and the examples still work without it, and on your own computer you can run the studio with a copy of the reference (On your own computer).
“contig chr17 is stored without its reference sequence”
The file was written without its reference plane (--no-ref), so anything that needs its bases needs the reference as well. In the Tools tab, fill in Its reference, which is filled in for you for a file made on GRCh38; in the terminal, add --reference /data/grch38/chr17.gpxil.tif; in Python, GpxilFile(path, reference=…). For a file made on another reference, give the FASTA file it was made from. The Viewer finds GRCh38 by itself.
“… does not match the md5 of chr17”, or “… has length …, not …”
The reference you gave isn’t the one the file was made on: another assembly, or another version of the chromosome. gpxil checks every reference against the checksums in the file, so that bases are never taken from the wrong one. gpxil info names the reference the file was made on.
gpxil encode notes that REF alleles don’t match the reference
The VCF was called against another reference, such as GRCh37 (hg19), so its variants are in the wrong places on this one. Encode it with the reference it was called against. A few mismatches can be harmless, such as variants in a VCF made from a different patch of the same assembly; gpxil info --json lists the first of them for each contig.
“VCF contigs not in the reference (skipped)”
The reference has no sequence of that name. Each file in /data/grch38 holds one chromosome, so a VCF of a whole genome encoded on chr17.gpxil.tif gives chromosome 17 only, and notes the others. Encode each chromosome with its own reference file, or use the whole-genome file on your own computer. Names with and without chr (17, chr17) are matched either way.
Most of a chromosome isn’t called (grey in the Variants view, near-black in the Genotype view)
That is what the file knows. With a BED file of the regions called with confidence, the bases outside them are UNKNOWN, because the VCF says nothing about them; Genome in a Bottle’s benchmark covers TP53 but not the whole of chromosome 17 (Turn someone’s VCF into a gpxil file).

Tools, pictures and genes

A tool says the region is too big for the browser
In the browser, a picture can show at most 25 million bases, and 64 million pixels; FASTA and VCF are written at most 50 million bases at a time; and the Viewer draws at most 4 million bases. Choose a smaller region, or fewer pixels per base. On your own computer, the same commands have no such limits.
gpxil2pxil can’t find a gene
“no gene … in the Gpxil browser’s genes”: check the gene’s symbol, or give its Ensembl ID (ENSG…). “… is an alias of …”: give one of the genes it names. The Gpxil browser’s genes are Ensembl’s on GRCh38, so for a file made on another reference, give a GTF file of that reference’s genes (Genes from, or -a). A gene on a chromosome the file doesn’t have needs a file that has it, such as the chromosome’s file in /data/grch38.
“… has no sample, so it has no haplotypes”
The file holds only a reference, such as the files in /data/grch38, so its pictures can only be of the reference: under From, choose the reference (--haplotypes ref).
A picture, PDF or gpxil file made in the terminal won’t open
It was written with >, which is for text. Make it again with -o FILE (The Terminal).
“… isn’t installed in this terminal”
The terminal has the gpxil programs, Python, and the common text and file programs (help lists them), but not bcftools, samtools, awk or gzip. The message says what to use instead. gpxil reads .vcf.gz and .fa.gz files as they are.
A workflow can’t run, or one of its steps failed
If the workflow can’t run, its Run page lists why, such as an input that isn’t connected. Open it in the editor, where Checks lists the same things and takes you to each step. If a step failed, open What went wrong under it: it shows the tool’s own error, the one you’d see if you ran the tool yourself, and the steps that read its files didn’t run. Put the step’s settings right in the editor, or choose another input file, and run it again (Workflows).
A workflow’s run says stopped
A workflow runs in this page, so closing or reloading the page stops it, and the steps that hadn’t run are marked stopped. The files of the steps that had finished are in the run’s folder. Run the workflow again.

Your files

My files have gone
Are you using the same browser, on the same computer, and not a private window? The browser keeps the files for this site only. If your browser clears site data when it closes, it deletes them too, so download anything you want to keep.
“… is larger than 1 GB … it isn’t kept in the browser”
A file that big is there while the page is open, but the browser won’t keep it. Download it before you leave. A gpxil file without its reference plane is a hundred times smaller.
“The browser has no more room for the studio’s files”
gpxil files are big. Download the files you want to keep, then delete those you no longer need from the Files tab. My files → Where are my files kept? shows how much room they take.
“The studio is open in another tab or window too”
Both tabs keep files in the same place, so one can overwrite what the other has saved. Close one of them.

Reporting a fault

If a tool fails and shows Python’s traceback (for reporting a fault) under the result, or a file the studio made doesn’t pass its own check, that’s a fault. Report it on the studio’s issues page, or on gpxiltools’ if it happens on your own computer too. Include the traceback and, if you can, a file that shows the problem: one of the examples, or a small made-up file such as the worked example. Never attach a person’s genome, or a picture of one.

Ideas, standards and data

  • The genome pixel image is Guenter Albrecht-Buehler’s idea: a genome drawn as pictures, one pixel a base. gpxil takes it from one sequence to a person’s genome, with their genotype at every base, and the gpxi palette keeps his four greys.
  • gpxil files are TIFF files, and they name their reference sequences by the GA4GH’s refget checksums. Variants come from VCF files, and bases are written in the IUPAC’s codes.
  • The GRCh38 reference is the Genome Reference Consortium’s, as Ensembl release 116 gives it, with Ensembl’s genes and transcripts, and MANE’s choice of transcripts; the Gpxil browser made them into the files the studio reads.
  • HG002’s genome in the examples is the Genome in a Bottle Consortium’s benchmark (NIST), version 4.2.1, for a man of the Personal Genome Project who agreed to its release; the examples were made from it with gpxiltools. TP53’s transcripts in TP53.gtf are Ensembl’s.
  • The worked example is the gpxil specification’s.
