Look inside a gpxil file, and check it

Someone has sent you a gpxil file, or you’ve made one. This walkthrough shows what it holds – its reference, its sample, its contigs and planes, its metadata – and how to check that it follows the gpxil specification. It uses HG002’s chromosome 17; with a file of your own, choose it instead.

1 · A first look, in the Files tab

Click a gpxil file in the Files tab. Without starting Python, the tab reads the file’s first page, where its metadata is, and shows what it holds: the reference it was made from, the sample, the layout, and a table of its contigs and their planes.

2 · Its pixels, in the Viewer

The Viewer shows the planes themselves. Choose a region and what to show; point at a pixel to see the values of every plane there.

3 · What’s in it, as gpxil says it

What’s in a gpxil file runs gpxil info. It gives the file’s format version, what wrote it and when, its reference and sample, and for each contig its length, its planes, how many VCF records went into it and how many entries its sidecar has (the inserted bases and complex variants that don’t fit in a pixel).

Tick All of its metadata, as JSON to see everything the file says about itself: each contig’s checksums (md5 and refget), the pages that hold its planes, how many bases were called with confidence, and the counts the encoder kept as it read the VCF, such as conflicts and ref_mismatches (both 0 here, as they should be). The gpxil format describes every key.

4 · Check it

Check a gpxil file runs gpxil validate. It checks the metadata against the specification’s JSON schema; that every contig has the pages its metadata names, of the right size and type; that every value of every plane is a code the specification allows; that the flags, phase sets and sidecar agree with each other; and, if you leave Recompute the sequences’ checksums ticked, that the reference plane’s bases give the MD5 and refget checksums in the metadata. That last check proves the bases are those of the reference the file names.

It should say Valid. An error means a reader can’t trust the file; a warning is worth reading but doesn’t make the file invalid. A file that isn’t gpxil at all, such as an ordinary TIFF picture, fails at once: its first page has no gpxil metadata.

5 · A file on the web

The files of the GRCh38 reference in /data/grch38 are on the Gpxil browser’s web site. Looking inside one reads only its first page, so it is as quick as a file of your own. Checking its checksums reads every base, which for chromosome 1 means downloading 67 MB, so untick Recompute the sequences’ checksums for a quick check of a big file on the web.

The same in the terminal

gpxil info /data/examples/HG002_chr17.gpxil.tif
gpxil info --json /data/examples/HG002_chr17.gpxil.tif > ~/results/HG002_chr17.metadata.json
gpxil validate /data/examples/HG002_chr17.gpxil.tif
gpxil info /data/grch38/chr1.gpxil.tif
gpxil validate /data/grch38/chrM.gpxil.tif

gpxil info --json prints the metadata as JSON; here it is saved in a file, which the Files tab shows neatly. gpxil validate --no-digests skips the checksums.

The same in Python

In a notebook, the metadata is a Python dictionary, and each contig an object with its name, length and planes:

from gpxiltools import GpxilFile
from gpxiltools.validate import validate

g = GpxilFile("/data/examples/HG002_chr17.gpxil.tif")
print(g.metadata["reference"])
print(g.metadata["sample"])
for c in g:
    print(c.name, f"{c.length:,} bases", c.planes, c.entry["md5"])

report = validate("/data/examples/HG002_chr17.gpxil.tif")
print("valid" if report.ok else "not valid", report.errors, report.warnings)
