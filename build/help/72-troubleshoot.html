When something goes wrong

These are the common problems, and what to do about each one.

Python and memory

“Python couldn’t start”
The first time you use it, the studio downloads Python (about 15 MB) from cdn.jsdelivr.net. If your network blocks that site, or you’re offline, the tools, the notebook and the programs can’t run, although the Viewer and the Files tab still work, because they read gpxil files in the page itself. Try again on another network. After the first time, the browser usually keeps a copy.
“Python stopped unexpectedly”, a MemoryError, or the page reloads by itself
Python ran out of memory. A browser tab has a few gigabytes at most, and some jobs need more: encoding holds about 6 bytes for each base of a chromosome, so chromosome 17 needs half a gigabyte and chromosome 1 about 1.5 GB, which may be too much; reading a whole chromosome’s planes at once in a notebook needs a byte a base for each plane. Reload the page: your files are kept. Then encode one chromosome at a time, read big regions in pieces, and do the biggest jobs on your own computer (A whole genome without running out of memory, Big files and memory, On your own computer).
A tool waits for a long time
A notebook cell may be running: the tools share the notebook’s Python, so they wait for it to finish. Stop the cell in the Notebook tab. The first tool of a visit also waits for Python to start, and a tool that reads the GRCh38 reference waits for its pieces to come from the web: encoding on chromosome 17 takes about a minute.

The reference

A file in /data/grch38 couldn’t be read
The studio reads the GRCh38 reference from the Gpxil browser’s site, comparativechrono.github.io, a piece at a time. Check that you’re online and that your network doesn’t block the site. Your own files and the examples still work without it, and on your own computer you can run the studio with a copy of the reference (On your own computer).
“contig chr17 is stored without its reference sequence”
The file was written without its reference plane (--no-ref), so anything that needs its bases needs the reference as well. In the Tools tab, fill in Its reference, which is filled in for you for a file made on GRCh38; in the terminal, add --reference /data/grch38/chr17.gpxil.tif; in Python, GpxilFile(path, reference=…). For a file made on another reference, give the FASTA file it was made from. The Viewer finds GRCh38 by itself.
“… does not match the md5 of chr17”, or “… has length …, not …”
The reference you gave isn’t the one the file was made on: another assembly, or another version of the chromosome. gpxil checks every reference against the checksums in the file, so that bases are never taken from the wrong one. gpxil info names the reference the file was made on.
gpxil encode notes that REF alleles don’t match the reference
The VCF was called against another reference, such as GRCh37 (hg19), so its variants are in the wrong places on this one. Encode it with the reference it was called against. A few mismatches can be harmless, such as variants in a VCF made from a different patch of the same assembly; gpxil info --json lists the first of them for each contig.
“VCF contigs not in the reference (skipped)”
The reference has no sequence of that name. Each file in /data/grch38 holds one chromosome, so a VCF of a whole genome encoded on chr17.gpxil.tif gives chromosome 17 only, and notes the others. Encode each chromosome with its own reference file, or use the whole-genome file on your own computer. Names with and without chr (17, chr17) are matched either way.
Most of a chromosome isn’t called (grey in the Variants view, near-black in the Genotype view)
That is what the file knows. With a BED file of the regions called with confidence, the bases outside them are UNKNOWN, because the VCF says nothing about them; Genome in a Bottle’s benchmark covers TP53 but not the whole of chromosome 17 (Turn someone’s VCF into a gpxil file).

Tools, pictures and genes

A tool says the region is too big for the browser
In the browser, a picture can show at most 25 million bases, and 64 million pixels; FASTA and VCF are written at most 50 million bases at a time; and the Viewer draws at most 4 million bases. Choose a smaller region, or fewer pixels per base. On your own computer, the same commands have no such limits.
gpxil2pxil can’t find a gene
“no gene … in the Gpxil browser’s genes”: check the gene’s symbol, or give its Ensembl ID (ENSG…). “… is an alias of …”: give one of the genes it names. The Gpxil browser’s genes are Ensembl’s on GRCh38, so for a file made on another reference, give a GTF file of that reference’s genes (Genes from, or -a). A gene on a chromosome the file doesn’t have needs a file that has it, such as the chromosome’s file in /data/grch38.
“… has no sample, so it has no haplotypes”
The file holds only a reference, such as the files in /data/grch38, so its pictures can only be of the reference: under From, choose the reference (--haplotypes ref).
A picture, PDF or gpxil file made in the terminal won’t open
It was written with >, which is for text. Make it again with -o FILE (The Terminal).
“… isn’t installed in this terminal”
The terminal has the gpxil programs, Python, and the common text and file programs (help lists them), but not bcftools, samtools, awk or gzip. The message says what to use instead. gpxil reads .vcf.gz and .fa.gz files as they are.
A workflow can’t run, or one of its steps failed
If the workflow can’t run, its Run page lists why, such as an input that isn’t connected. Open it in the editor, where Checks lists the same things and takes you to each step. If a step failed, open What went wrong under it: it shows the tool’s own error, the one you’d see if you ran the tool yourself, and the steps that read its files didn’t run. Put the step’s settings right in the editor, or choose another input file, and run it again (Workflows).
A workflow’s run says stopped
A workflow runs in this page, so closing or reloading the page stops it, and the steps that hadn’t run are marked stopped. The files of the steps that had finished are in the run’s folder. Run the workflow again.

Your files

My files have gone
Are you using the same browser, on the same computer, and not a private window? The browser keeps the files for this site only. If your browser clears site data when it closes, it deletes them too, so download anything you want to keep.
“… is larger than 1 GB … it isn’t kept in the browser”
A file that big is there while the page is open, but the browser won’t keep it. Download it before you leave. A gpxil file without its reference plane is a hundred times smaller.
“The browser has no more room for the studio’s files”
gpxil files are big. Download the files you want to keep, then delete those you no longer need from the Files tab. My files → Where are my files kept? shows how much room they take.
“The studio is open in another tab or window too”
Both tabs keep files in the same place, so one can overwrite what the other has saved. Close one of them.

Reporting a fault

If a tool fails and shows Python’s traceback (for reporting a fault) under the result, or a file the studio made doesn’t pass its own check, that’s a fault. Report it on the studio’s issues page, or on gpxiltools’ if it happens on your own computer too. Include the traceback and, if you can, a file that shows the problem: one of the examples, or a small made-up file such as the worked example. Never attach a person’s genome, or a picture of one.
