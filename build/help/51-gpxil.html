The gpxil format

A gpxil file stores a genome as pictures: one pixel a base, one picture for each chromosome and each kind of information, in an ordinary multi-page TIFF file. Any image software opens it as a picture of the genome; image libraries read its pictures as arrays of numbers; and it holds the reference and one person’s genotypes exactly, so they can be got back base for base. This page describes the format; the specification, version 0.1 (a draft), gives every rule.

Contigs and planes

A gpxil file has a list of contigs – chromosomes, the mitochondrion, unplaced scaffolds – and each contig has one or more planes: arrays with one value for each of its bases. Every plane is lined up with the reference, so the same pixel is the same position in every plane, and in every person’s file.

PlaneTypeWhat it holds
ref8-bitthe reference base, as an IUPAC code, and whether it is soft-masked (lower case: in a repeat)
gt8-bitthe person’s genotype: what each of their two haplotypes has at this base, four bits each
flags8-bitwhether the call here was phased, an insertion follows, the call was filtered, a call covers the base
gq, dp8-bitthe genotype quality and read depth of the call over the base, up to 254; 255 where there is none
ps32-bitthe phase set of a phased call; 0 where there is none
x-…8, 16 or 32 bits, or floating pointplanes of your own, such as x-methylation; readers ignore those they don’t know

A file holds at most one person. One without a person is a reference – ref planes only, like the chromosomes of GRCh38 in /data/grch38. A file can also leave the ref plane out and name its reference by checksums instead (below). A contig with a gt plane always has a flags plane too. The codes gives every value.

Layout: bases in rows

Each plane is a picture W pixels wide, filled like a page of text: base i, counting from 0, is in row i ÷ W and column i mod W, and the end of the last row is padded with zeros. The writer chooses the width and records it for each contig. gpxiltools uses 8,192, so chromosome 17’s 83,257,441 bases make pictures of 10,164 rows.

A plane is really a line of values, so any program can re-wrap it to another width without losing anything. A width equal to a repeat’s period lines the repeat up in columns. Other views, such as a book’s pages or a Hilbert curve, are made from the rows when they are drawn.

Pages: one picture for each plane

Every plane of every contig is one page of the TIFF file. The pages go contig by contig, in the order ref, gt, flags, gq, dp, ps, then planes of your own. Each page describes itself in JSON, such as {"gpxil": "0.2", "contig": "chr17", "plane": "gt", "length": 83257441}, and has a name for image viewers, such as chr17 gt. The first page also carries the metadata of the whole file.

The ref, gt and flags pages are palette pictures with a colour map, so that an ordinary image viewer shows them in colour. The colours are only for looking: no reader takes values from them. The other pages are greyscale.

Strips: reading a region

Each page is cut into strips of whole rows, and each strip is compressed on its own with Deflate (zlib), which every TIFF reader understands. gpxiltools makes strips of 256 KB before compression: 32 rows of 8,192 bases – 262,144 bases – for an 8-bit plane, and 8 rows for the 32-bit ps. To read a region, a reader works out the rows it covers and decompresses only their strips. So a gene costs the same to read from a file of one chromosome as from a file of the whole genome, and over the web only those strips need fetching (Big files and memory).

The sidecar: what doesn’t fit in a pixel

An insertion happens between two bases, so it has no pixel of its own. The flags plane marks the base it follows (INS1 or INS2, by haplotype), and the inserted bases go in the contig’s sidecar: a small table, compressed, in a private tag of the gt page (tag 65400). The sidecar also describes complex variants, such as inversions, which can’t be written base by base. This is the sidecar of the specification’s worked example – two Gs inserted after offset 7, on both haplotypes:

#gpxil-sidecar	0.1
offset	hap	kind	data
7	1	INS	GG
7	2	INS	GG

Programs built on libtiff, such as ImageMagick, warn about the unknown tag and otherwise ignore it.

The metadata

The first page’s description is a JSON object that says what the file holds. It must have gpxil (the version of the specification whose rules made it, "0.2"; files made by gpxiltools 0.5 or earlier say "0.1", and read the same), layout (the default width), contigs and, in a file with a person, sample. Usually there too are reference (its name and source file), planes (their types and missing values), palette, generator, created and summary, the encoder’s totals. Each contig’s entry gives:

KeyWhat it holds
name, length, widththe contig’s name, its number of bases, and its layout width
pageswhich page holds each plane: {"ref": 0, "gt": 1, "flags": 2, …}
md5, refgetthe checksums of its reference sequence (below)
aliasesother names for it, such as 17 for chr17
ploidy1 if haplotype 2 is ABSENT everywhere, 2 if nowhere, otherwise "mixed"
encoding, callable_bases, sidecar_entries, phase_setswhat the encoder did (records applied, conflicts, mismatches with the reference …), the bases in the callable regions, the sidecar’s entries, and the phase sets

The sample object names the person (id, as in the VCF) and records what was applied: the VCF, the callable regions, the haploid regions and the sex. Readers ignore keys they don’t know, so writers can add their own.

Checksums: naming the reference

Each contig’s reference sequence has two checksums: its MD5, as in a SAM or CRAM header (@SQ M5), and its GA4GH refget identifier (SQ. and 32 characters). Both are worked out from the sequence in capital letters. They let a file written without its ref plane say exactly which reference it needs, and they let a reader check that a reference it is given is that one: gpxiltools refuses a reference whose checksums don’t match. For a FASTA file of plain IUPAC letters, they are the checksums other tools work out.

Why TIFF

  • Every image program opens it, so a gpxil file is a picture of the genome before it is anything else, and can be printed as one.
  • Image libraries – tifffile, Pillow, and those of image analysis – read its pages as arrays, so image operations become genome operations: the difference of two people’s gt planes, say, or a box filter over the G and C bits of ref for the GC content.
  • Strips give random access, and standard compression keeps files small: HG002’s chromosome 17, with all six planes, is 24.6 MB, and the whole of GRCh38 is 848.5 MB.
  • A file over 4 GB has to be a BigTIFF, which gpxiltools switches to by itself. A whole human genome with one person is under 1 GB.

Look for yourself

gpxil info /data/examples/HG002_chr17.gpxil.tif
gpxil info --json /data/examples/worked-example.gpxil.tif

In Python, tifffile reads a gpxil file as the ordinary TIFF it is, and Pillow sees a palette picture of six frames:

import json
import tifffile
from PIL import Image

with tifffile.TiffFile("/data/examples/HG002_chr17.gpxil.tif") as tif:
    meta = json.loads(tif.pages[0].description)
    print(sorted(meta))
    for page in tif.pages:
        print(page.index, page.tags["PageName"].value, page.shape, page.dtype,
              f"{len(page.dataoffsets)} strips of {page.rowsperstrip} rows", "sidecar" if 65400 in page.tags else "")
with Image.open("/data/examples/HG002_chr17.gpxil.tif") as im:
    print(im.mode, im.size, im.n_frames)
